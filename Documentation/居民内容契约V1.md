# 居民内容契约 V1

## 目标

本文件定义居民内容生产线当前已经落地的基础契约：Stable ID、Name V2、LifeTag、Occupation Group、LifeEvent Eligibility / Effect、Appearance Authoring，以及 Web Snapshot / Compiled Definitions 的稳定字段。

Web Demo 继续用于玩法和内容验证；这些契约面向后续 Content Compiler、Unity Runtime 与存档兼容。

---

## Stable ID

所有需要被其它内容引用、进入运行时数据库或写入存档的 Definition，都必须拥有稳定 ID。

示例：

```text
occupation.carpenter
occupation-group.craft
routine.work.carpenter.tool-maintenance
lifeevent.service-draft
name.surname.lu
name.given.male.mingyuan
lifetag.served-military
appearance.hair.tied-01
appearance.palette.clothing.indigo-01
```

规则：

- 使用小写 ASCII。
- 使用 `.` 表达命名空间。
- 任意片段内部可以使用 `-`。
- 显示文本修改不得导致 Stable ID 修改。
- 数组顺序不得作为长期身份。
- Stable ID 在全居民内容域中必须唯一。

ContentContractCompiler 会把 Name、LifeTag、Occupation Group、Occupation、Routine、LifeEvent、Appearance Part / Palette 注册到统一 Stable ID Registry，并检查格式、重复 ID 与 FNV-1a 32 hash 冲突。

生成文件：

```text
Web/public/generated/stable-id-registry.json
```

当前 hash 契约为 `fnv1a32-utf16`。Web 阶段主要用于提前发现冲突；未来 Unity 可以在构建时把 Stable ID 解析成紧凑 RuntimeIndex，但存档层不依赖易变数组下标。

## Name V2

姓名 Authoring 不做任意汉字笛卡尔组合。Given Name 使用已经审核过的完整 token，例如“明远、景和、静和、知微”。

唯一姓名 Authoring 源：

```text
Content/Names/surnames-v2.json
Content/Names/given-names-v2.json
```

ResidentGenerator 直接消费编译后的 `name-catalog-v2.json`，按 `weight`、性别与 `generationGroups` 选取 token，并直接写入：

```text
surnameId
givenNameId
displayName
surname
```

当前 Demo 的姓名代际映射：

```text
0～24   young
25～49  middle
50+     old
```

若 token 未填写 `generationGroups`，表示所有代际可用。姓名允许重复，不做全城唯一性检查。

家庭规则：Household 先生成；子女通常继承父系 `surnameId`；配偶保留原姓。ResidentSnapshotCompiler 会再次校验姓氏继承。

正式 Unity Runtime 不要求长期保存 `displayName` 字符串；可以由 Stable ID / RuntimeIndex 回查定义。

## LifeTag Registry

LifeTag 是居民过去重要经历的紧凑事实，不是玩家成就，也不保存故事正文。

Authoring：

```text
Content/Tags/life-tags.json
```

LifeEvent 可以读取：

```json
{
  "eligibility": {
    "requiredTags": ["lifetag.served-military"],
    "forbiddenTags": ["lifetag.widowed"]
  }
}
```

也可以写入：

```json
{
  "effects": {
    "addTags": ["lifetag.served-military"],
    "removeTags": []
  }
}
```

当前已经存在真实连续性链：

```text
服役故事完成
↓
lifetag.served-military
↓
多年后
↓
“旧同伍进城了”进入候选池
```

ResidentGenerator 在生成背景人生时按时间顺序维护临时 LifeTag；ResidentSnapshotCompiler 再按最终 Life Chapter 重放 Effect 验证最终状态。

Web Snapshot 当前使用 `string[]` 方便调试；正式 Unity Runtime 目标仍是 bitset / RuntimeIndex 等紧凑表示。

## Occupation Group

每个 Occupation 拥有稳定 `groupId`：

```json
{
  "id": "occupation.carpenter",
  "groupId": "occupation-group.craft"
}
```

Occupation Group 用于 Story Bucket、Appearance 过滤与 Coverage，不代表社会阶层。

LifeEvent 可以同时使用：

```text
occupations       精确职业条件
occupationGroups  粗职业组条件
```

两者同时存在时必须同时满足。

详细 Story Bucket 规则见：

```text
Documentation/StoryBucket与内容覆盖V1.md
```

## Routine Library V2

Routine Authoring 位于 `Content/Routines/routine-templates.json`，Schema 为 `wanhu.routines.v2`；完整命名、写作和批次工作流见 `Documentation/日常事件库V2.md`。

新 ID 固定使用 `routine.<domain>.<scope>.<action>`。已注册的 V1 ID 作为历史 Stable ID 保留，不批量重命名。每个定义包含 category、sourceFacts、显式 eligibility、weight、cooldownDays 与 variants。

ContentContractCompiler 会生成 `routine-catalog-v2.json`，按 Stable ID 为当前内容构建分配稠密 RuntimeIndex。RuntimeIndex 用于 ECS / UI 热路径查表，但不是跨内容版本的永久身份；存档层仍需 Stable ID 或版本化 remap。

VariantIndex 在记录创建时确定。已发布 Variant 只允许末尾追加，不允许重排后改变旧索引含义。R1 收尾后固定质量门禁：单条 Variant 最长 24 个 Unicode 字符；全库按 NFKC、空白与常用标点归一化后不得出现重复文本；`sourceFacts` 顶层域必须与 Routine `category` 一致。

## LifeEvent Effect

### 轻量 Effect

当前已实际执行的轻量 Effect：

```text
addTags
removeTags
```

它们只修改当前居民自己的紧凑事实，可以安全用于背景人生生成和 Web Runtime 条件判断。

### 结构型 Effect Request

LifeEvent 现在拥有结构变更请求契约：

```json
{
  "effects": {
    "structuralRequests": [
      {
        "type": "changeOccupation",
        "occupationId": "occupation.carpenter"
      }
    ]
  }
}
```

当前允许四类请求：

```text
changeOccupation
moveHousehold
formMarriage
addChild
```

`moveHousehold` 当前支持策略：

```text
same-district
different-district
any-district
```

重要边界：

> `structuralRequests` 当前是内容与 Compiler 契约，不代表 Web Demo 已经直接执行这些结构变化。

未来 Unity Runtime 中，故事系统只产生 Request；真正修改 Occupation、Household、Marriage、Child 等跨实体结构的行为必须交给集中结构系统处理，再统一使用 ECB / 对应结构命令执行。居民并行 Job 不直接修改其它 Entity。

ContentContractCompiler 会校验请求类型、目标职业、搬家策略、重复请求和数量上限。

## Appearance Authoring V1

正式外观数据从 `PortraitSeed` 进一步拆成可持久化的 AppearanceDNA。

Authoring：

```text
Content/Appearance/appearance-parts.json
```

Schema：

```text
Schemas/appearance.schema.json
```

当前 Part Slot：

```text
face
hair
brow
facial-hair
headwear
outfit
```

Palette Slot：

```text
skin
hair
clothing
```

每个条目拥有 Stable ID、权重，并可按以下条件过滤：

```text
genders
lifeStages
occupationGroups
```

示例：

```json
{
  "id": "appearance.outfit.craft-work-01",
  "slot": "outfit",
  "label": "工匠短褐",
  "weight": 7,
  "occupationGroups": ["occupation-group.craft"]
}
```

当前 Authoring 只定义“居民选择了什么外观部件”，不绑定 Unity Prefab、Mesh、Sprite 的最终加载实现。`assetKey` 预留给未来资源映射。

## AppearanceDNA

ResidentAppearanceCompiler 使用居民 Seed + 性别 + LifeStage + OccupationGroup，从 Appearance Catalog 确定性选出一组稳定外观身份：

```text
faceId
hairId
browId
facialHairId
headwearId
outfitId
skinPaletteId
hairPaletteId
clothingPaletteId
```

Web Snapshot 现在保存这组 Stable ID，因此后续 UI Portrait 和 3D Character 可以共享同一组识别特征。

Web Demo 仍保留 `portraitSeed` 作为兼容 / 调试字段，但它不再是正式外观身份的唯一来源。

需要区分：Web Snapshot 每次构建仍可以按同一 Seed 重新生成 AppearanceDNA；正式游戏一旦创建居民，就应把选中的 AppearanceDNA 保存到存档，避免未来资源池扩充导致老居民变脸。

## Resident Snapshot V3

Web Demo 最终快照当前为：

```text
wanhu.resident-snapshot.v3
```

稳定身份相关字段包括：

```text
surnameId
givenNameId
lifeTags[]
appearance
```

当前编译流程：

```text
ContentContractCompiler
↓
StoryCompiler
↓
ResidentGenerator
↓
LifeEventCompiler
↓
StoryBucketCompiler
↓
ResidentSnapshotCompiler
↓
ResidentAppearanceCompiler
↓
WebContentCompiler
```

其中 ResidentAppearanceCompiler 将 Snapshot V2 升级为 Snapshot V3。

这仍然是 Web / Prototype 数据，不代表 Unity ECS 直接使用 JSON 或字符串数组。

## Compiled Definitions V4

Web 最终只读 Definition Bundle 当前为：

```text
wanhu.resident-definitions.v7
```

`WebContentCompiler` 把已有中间产物收拢到一个最终 Web Bundle：

```text
nameCatalog
lifeTags
occupationGroups
occupations
routines
lifeEvents
generation
appearanceCatalog
storyBuckets
contentMeta
```

因此 Web 玩法代码以后可以只消费最终 `definitions.json`，不需要再分别读取 Story Bucket、Appearance Catalog 或其它 Authoring 文件。

`contentMeta` 只提供编译结果数量等调试信息，不是正式游戏规则。

## Reference Validation

ContentContractCompiler 当前检查：

```text
Stable ID 格式 / 重复 / hash collision
Name token 唯一性 / 性别 / 权重
Occupation → Occupation Group
Routine V2 → Stable ID 命名 / Fact ID 格式 / Occupation / Occupation Group / LifeStage / Gender / Variant / Cooldown
LifeEvent → Occupation / Occupation Group
LifeEvent Eligibility → LifeTag
LifeEvent Tag Effect → LifeTag
LifeEvent Structural Request → Occupation / Policy
Appearance → Occupation Group
Appearance slot / gender / lifeStage / weight
Appearance 必需槽位覆盖
```

原则是：引用错误在 Web Build 之前失败，而不是等运行时才发现。

## Coverage Report

`content-coverage.json` 当前统计：

```text
姓名池数量
Appearance Part / Palette 数量与槽位覆盖
LifeTag 使用 / 产出数量
不同人生阶段 LifeEvent / Life Chapter 数量
Routine 定义 / Variant / category 数量与各职业可用 Routine 数量
Routine 文本最短 / 最长 / 平均长度、Fact 数量与 Fact 复用清单
各职业 LifeEvent / Life Chapter / Routine 数量
各 Occupation Group 内容数量
Structural Request 各类型使用数量
未使用 LifeTag 与明显缺口 warning
```

Coverage warning 暂时不导致 Build 失败。它用于后续批量生产时决定下一批最需要补的内容，而不是只追求故事总数。
