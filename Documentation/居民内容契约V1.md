# 居民内容契约 V1

## 目标

本文件定义居民内容生产线第一阶段需要稳定下来的基础契约：Stable ID、LifeTag、Name V2、Occupation Group、LifeEvent Eligibility / Effect，以及 Web Snapshot 的稳定身份字段。

Web Demo 继续用于玩法和内容验证；这些契约面向后续 Content Compiler、Unity Runtime 与存档兼容。

---

## Stable ID

所有需要被其它内容引用、进入运行时数据库或写入存档的 Definition，都必须拥有稳定 ID。

示例：

```text
occupation.carpenter
occupation-group.craft
routine.carpenter.tool
lifeevent.service-draft
name.surname.lu
name.given.male.mingyuan
lifetag.served-military
```

规则：

- 使用小写 ASCII。
- 使用 `.` 表达命名空间。
- 任意片段内部可以使用 `-`。
- 显示文本修改不得导致 Stable ID 修改。
- 数组顺序不得作为长期身份。
- Stable ID 在全居民内容域中必须唯一。

ContentContractCompiler 会把 Name、LifeTag、Occupation Group、Occupation、Routine、LifeEvent 注册到统一 Stable ID Registry，并检查格式、重复 ID 与 FNV-1a 32 hash 冲突。

生成文件：

```text
Web/public/generated/stable-id-registry.json
```

当前 hash 契约为 `fnv1a32-utf16`。Web 阶段主要用于提前发现冲突；未来 Unity 可以在构建时把 Stable ID 解析成紧凑 RuntimeIndex，但存档层不依赖易变数组下标。

## Name V2

姓名 Authoring 不做任意汉字笛卡尔组合。Given Name 使用已经审核过的完整 token，例如“明远、景和、静和、知微”。

当前唯一姓名 Authoring 源：

```text
Content/Names/surnames-v2.json
Content/Names/given-names-v2.json
```

旧 V1 字符串池已经退出内容源，不再由 Generator 或 Compiler 读取。

Surname：

```json
{
  "id": "name.surname.lu",
  "text": "陆",
  "weight": 1
}
```

Given Name：

```json
{
  "id": "name.given.male.mingyuan",
  "text": "明远",
  "gender": "male",
  "weight": 1
}
```

可扩展字段：

```text
styles
generationGroups
```

`ResidentGenerator` 现在直接消费编译后的 `name-catalog-v2.json`：

```text
Name V2 Authoring
↓
ContentContractCompiler
↓
name-catalog-v2.json
↓
ResidentGenerator
├─ weight 加权
├─ gender / unisex 筛选
├─ generationGroups 筛选
└─ 直接写 surnameId / givenNameId
```

当前年龄到姓名代际的 Demo 映射为：

```text
0～24   young
25～49  middle
50+     old
```

若 token 未填写 `generationGroups`，表示所有代际都可用。这个规则用于避免以后所有年龄层完全共享同一套名字风格，不代表真实朝代命名史。

最终生成的 Resident Snapshot 同时保存：

```text
surnameId
givenNameId
displayName   # Web / Debug 方便显示
surname       # Web / Debug 兼容字段
```

正式 Unity Runtime 不要求长期保存 `displayName` 字符串；可以由 Stable ID / RuntimeIndex 回查 Definition。

家庭规则保持：Household 先生成，子女通常继承父系姓氏，配偶保留原姓。Generator 直接传递 `surnameId`，SnapshotCompiler 会再次验证存在父亲引用的子女没有破坏姓氏继承规则。

## LifeTag Registry

LifeTag 是居民过去重要经历的紧凑事实，不是玩家成就，也不保存故事正文。

Authoring：

```text
Content/Tags/life-tags.json
```

示例：

```json
{
  "id": "lifetag.served-military",
  "label": "曾经服役",
  "category": "experience"
}
```

Web Snapshot 当前用 `string[]` 保存 LifeTag，是为了调试和验证；正式 Unity Runtime 目标仍是编译成 bitset / RuntimeIndex 等紧凑表示。

---

## LifeEvent Tag Eligibility

LifeEvent 可以根据居民过去经历筛选：

```json
{
  "eligibility": {
    "requiredTags": ["lifetag.served-military"],
    "forbiddenTags": ["lifetag.widowed"]
  }
}
```

语义：

- `requiredTags`：全部拥有才允许进入候选池。
- `forbiddenTags`：任意一个存在就排除。
- 同一标签不能同时出现在 required / forbidden。
- 引用必须存在于 LifeTag Registry。

这类条件只读取居民自己的紧凑状态，不需要扫描人生正文或查询其它居民。

当前已经存在一条真实连续性验证：

```text
服役故事完成
↓
lifetag.served-military
↓
几年后
↓
“旧同伍进城了”进入候选池
```

---

## LifeEvent Tag Effect

当前第一批 Effect 只实现 LifeTag：

```json
{
  "effects": {
    "addTags": ["lifetag.served-military"],
    "removeTags": []
  }
}
```

`ResidentGenerator` 在生成背景人生时会按人生阶段顺序维护临时 LifeTag 集合，因此依赖过去经历的 Story 不会凭空出现在更早阶段。

`ResidentSnapshotCompiler` 再按最终 Life Chapter 时间顺序重放这些轻量 Tag Effect，得到当前 `lifeTags`，用于验证生成结果与运行时条件一致。

后续真正修改职业、家庭、居所等结构的 Effect 不直接塞进当前 Tag Effect。它们会单独形成低频结构命令契约，例如 ChangeOccupation / Marriage / MoveHousehold。

## Occupation Group

每个 Occupation 现在拥有稳定 `groupId`：

```json
{
  "id": "occupation.carpenter",
  "groupId": "occupation-group.craft"
}
```

Occupation Group 用于大故事库的粗筛与 Coverage，不代表社会阶层。

LifeEvent 可以使用：

```text
occupations       精确职业条件
occupationGroups  粗职业组条件
```

两者同时存在时必须同时满足。

详细规则见：

```text
Documentation/StoryBucket与内容覆盖V1.md
```

## Resident Snapshot V2

Web Demo 的最终生成快照：

```text
wanhu.resident-snapshot.v2
```

稳定身份相关字段：

```text
surnameId
givenNameId
lifeTags[]
```

流程：

```text
ContentContractCompiler
↓
Name V2 / Stable ID / LifeTag / Occupation Group compiled data
↓
ResidentGenerator
├─ 直接生成 Stable Name ID
├─ Household 姓氏继承
└─ 按阶段生成背景 Life Chapter
↓
LifeEventCompiler
↓
StoryBucketCompiler
↓
ResidentSnapshotCompiler
├─ Stable Name ID 与显示文本一致性校验
├─ LifeEvent Effect → LifeTag 重放
├─ 家庭姓氏继承校验
└─ 输出最终 Snapshot V2
```

这仍然是 Web / Prototype 数据，不代表 Unity ECS 直接使用 JSON 或字符串数组。

## Reference Validation

ContentContractCompiler 当前检查：

```text
Stable ID 格式 / 重复 / hash collision
Occupation → Occupation Group
Routine → Occupation
LifeEvent → Occupation
LifeEvent → Occupation Group
LifeEvent Eligibility → LifeTag
LifeEvent Effect → LifeTag
Name token 唯一性 / 性别 / 权重
```

原则是：引用错误在 Web Build 之前失败，而不是等运行时才发现。

## Coverage Report

每次 `build-content` 会生成：

```text
Web/public/generated/content-coverage.json
```

当前统计：

```text
姓名池数量
LifeTag 使用 / 产出数量
不同人生阶段 LifeEvent 数量
不同人生阶段 Life Chapter 数量
各职业 LifeEvent / Life Chapter / Routine 数量
各 Occupation Group 内容数量
未使用 LifeTag 与明显缺口 warning
```

Coverage warning 暂时不导致 Build 失败。它用于后续批量生产时回答：

> 下一批内容最应该补哪里？

而不是只按“再写 100 条故事”推进。

## Build 契约

`npm run build-content` 当前顺序：

```text
ContentContractCompiler
↓
StoryCompiler
↓
ResidentGenerator
↓
LifeEventCompiler
↓
StoryBucketCompiler
↓
ResidentSnapshotCompiler
```

核心 generated 文件：

```text
stable-id-registry.json
name-catalog-v2.json
life-tags.json
occupation-groups.json
content-coverage.json
story-buckets.json
stories.json
definitions.json
resident-snapshot.json
```

GitHub Build 会把 `Web/public/generated/*.json` 上传为 `resident-generated-data` Artifact，使内容契约和编译结果可以脱离 Web UI 单独审查。
