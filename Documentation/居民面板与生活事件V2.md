# 居民面板与生活事件 V2

## 目标

玩家点击居民时，界面不是替居民生成一段“综合近况”，而是直接展示可验证的事实与经历：

1. 他是谁？
2. 他属于哪里？
3. 他现在在做什么？
4. 他正在经历或最近发生了什么？
5. 他过去有哪些值得记住的人生章节？

居民的一生由多个不同阶段发生的故事共同组成，而不是长期绑定一条“当前故事”。

---

## 玩家面板结构

```text
Resident Panel
├─ Identity
│  ├─ 头像
│  ├─ 姓名 / 年龄 / 职业
│  └─ 居住区域 / 家庭摘要
├─ World Links
│  ├─ 住处
│  ├─ 工作地
│  └─ 家人
├─ Current Activity
├─ Current / Recent LifeEvent
├─ Recent Routine
├─ Life History
└─ Follow Action
```

玩家面板不显示 Story ID、Branch、Stage、D+、分支数量和预制剧情进度。

---

## 不再保存独立“近况摘要”

不再定义居民级的 `Current Summary / 近况` 字段，也不在 LifeEvent Stage 中保存 `summary`。

原因是一个居民可能同时受到工作、家庭、城市工程、天气和个人故事影响。若强行把这些状态压缩成一句“近况”，就需要额外解决优先级、冲突、过期和文本组合问题，最终会形成另一套难维护的状态摘要系统。

面板直接展示：

```text
此刻
正在木作铺里做一件新活

正在经历
[当前 LifeEvent]

最近
[若干 Routine]
```

事件结束后，`Current Activity` 回到职业 / 当前状态推导，不需要再补一句“已经恢复原来的生活”。

例如服役故事最终 Stage 可以写“终于回到家里”，但系统不会额外保存“服役结束，已经回家并准备恢复原来的生活”这种总结字段。

---

## 三层信息结构

居民生活记录分成三个视觉与数据层级。

### Routine

普通生活的小记录，例如买东西、收工、整理铺子。

- 数量多
- 生命周期短
- 使用有限容量
- 不进入人生经历

### LifeEvent

当前或最近发生的一件具体事情。

- 通常 3 个阶段
- 当前阶段完整展示
- 同一事件的旧阶段只作为轻量前情
- 可以临时覆盖 `Current Activity`
- 默认不会永久进入人生经历

### Life Chapter

值得长期记住的人生章节。

- 成婚、开始营生等事实变化
- 服役、第一次独立做活等重要故事
- 长期保存在 `majorLifeHistory`
- 在“人生经历”中按年龄展示

因此：

```text
Routine ≠ LifeEvent ≠ Life Chapter
```

不是所有发生过的事情都值得永久保存。

## LifeEvent V2

### 基本字段

```text
id
weight
eligibility
source?
recordToHistory?
stages[3]
  delayDays
  title
  text
  activityOverride?
```

LifeEvent V2 不再包含 `summary` 字段。Stage 自身的 `title + text` 已经负责表达当下发生的事情；需要影响“此刻”时使用 `activityOverride`。

### `recordToHistory`

只有真正值得成为人生章节的事件才设置：

```json
{
  "recordToHistory": true
}
```

例如：

- 被征召服役
- 第一次独立完成正式工作
- 第一次独自替家里办事
- 孩子开始入学
- 晚年形成新的稳定生活方式

普通天气、订单增多、施工绕路等事件默认只属于当时生活，不进入永久人生历史。

完成后的重要 LifeEvent 用 `sourceEventId` 写入 `majorLifeHistory`。人生面板需要展开该章节时，再通过 `sourceEventId` 回查 LifeEvent Definition，因此不需要把完整三阶段正文复制进每个居民存档。

---

## 当前事件的可见周期

LifeEvent 的最终阶段并不等于永久占据玩家面板。

当前 Web 验证规则：

- Stage 1 / Stage 2：属于“正在经历”。
- Stage 3：短时间内属于“最近发生”。
- 完成 14 天以后：从主面板的当前事件区域退出。
- 若 `recordToHistory = true`：仍可在“人生经历”中长期查看。
- 若 `recordToHistory` 未开启：结束后只留下短期生活痕迹，不进入永久历史。

这样可以避免两个月前已经结束的事件持续占据居民面板视觉中心。

---

## 人生由多次故事抽取组成

居民不在出生时确定一条固定人生剧本。

模型是：

```text
居民状态
+
年龄阶段
+
职业 / 家庭条件
+
世界状态
+
过去的重要经历
↓
Eligible Story Pool
↓
低频加权抽取
↓
Story Thread / LifeEvent
↓
完成后按重要度决定是否成为 Life Chapter
```

同一个居民会在不同人生阶段多次进入不同故事池。

当前 Web 快照生成器已经按年龄阶段对 `recordToHistory` 故事进行确定性抽取：

```text
10～17
18～25
26～39
40～57
58+
```

同一 Seed 会稳定得到相同历史；不同居民不会固定拥有相同数量的精彩故事。

故事密度由 Seed 决定：有些居民经历较多，有些居民人生更平稳。系统不要求每个年龄阶段都强行发生重大事件。

---

## 多故事线的边界

“多故事线”指一个居民的一生由多条独立或弱关联 Story Thread 组成，不代表要建立完整社会关系图。

运行时允许未来同时存在少量 Story Thread，但玩家面板不需要把所有线程同时展开。默认只展示当前最值得关注的一件事，其余线程可以作为轻量状态存在。

推荐关系：

```text
约 80% 故事独立完成
约 20% 重要故事留下可复用的人生痕迹
```

后续可以通过轻量 `LifeTag / Story Anchor` 让未来故事读取过去结果，例如“曾经服役”“曾独立开铺”“曾经迁居”。这些标签只服务稀疏故事筛选，不做高频关系传播。

---

## Source：把居民和城市连起来

LifeEvent 可以携带一个轻量 `source`：

```json
{
  "type": "city",
  "label": "北市坊排水工程"
}
```

支持：

- `city`：城市建设或政策变化
- `family`：家庭内部变化
- `work`：营生和工作环境
- `weather`：天气 / 节令
- `personal`：普通个人生活

Source 的价值是让玩家感受到城市建设正在作用到具体的人，而不是建立复杂依赖网络。

## 人生经历 UI

“人生经历”的计数表示人生章节数量，不表示 LifeEvent Stage 数量，也不包括 Routine 数量。

时间轴按发生年龄展示：

```text
14岁 · 第一次独自替家里办事
22岁 · 成了家
27岁 · 轮到我去服役
31岁 · 家里添了孩子
34岁 · 开始做木工
```

若该章节来自预制 LifeEvent，玩家可以继续展开，读取该故事原本的三阶段文本。

事实型章节如“成了家”“开始做木工”可以只显示一行，不需要伪造文学正文。

---

## 性能边界

常规故事选择只读取：

```text
Resident 自己的数据
+ Household 少量冷数据
+ Global / Definition 只读数据
+ 少量已保存人生章节 / 标签
```

不查询朋友、不遍历邻居、不沿家谱传播状态。

真正修改职业、家庭、居住地等结构时，仍通过低频结构命令系统处理。

居民系统的重点是：

> 用少量稳定数据和稀疏故事，让玩家相信这个人过去真的生活过。
