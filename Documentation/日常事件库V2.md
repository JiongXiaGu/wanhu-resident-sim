# 日常事件库 V2

## 目的

Routine 是居民近期生活里可以被反复看见的小事，不是人生大事件，也不是行为树日志。内容层用 Stable ID 和可读 JSON 维护；运行时通过紧凑 RuntimeIndex 查表，ECS 不保存中文字符串。

当前阶段为 **R1 已完成，下一步进入 R2 职业日常**。R0 契约、R1 两轮扩库与 Batch 3 质量收尾均已完成；后续不再以泛居民条目数量为主目标，而是按职业与 Occupation Group 补专属日常。

## Stable ID 命名

新 Routine 一律使用：

```text
routine.<domain>.<scope>.<action>
```

固定 domain：

```text
household  家庭与居家
work       工作、手艺、劳动
study      学习、私塾、学徒学习
market     买卖、消费、市场
social     邻里、朋友、同事交往
travel     出行、跑腿、往返
leisure    闲暇、娱乐、休息
community  井、河、街巷与公共生活
care       照料、看病、育儿、养老
custom     节令、民俗、庙会等
```

`scope` 表示主要适用对象，优先使用 `common` 或已有职业 Stable ID 的末段，例如 `carpenter`、`student`、`vendor`。`action` 必须描述已完成的具体行为，不使用 `tool`、`friend`、`food` 这种模糊名词。

示例：

```text
routine.work.carpenter.tool-maintenance
routine.study.student.copy-lesson
routine.market.common.buy-household-goods
routine.social.common.chat-with-neighbor
routine.community.common.fetch-water
```

天气、年龄、性别、职业组不是命名空间，放入 eligibility。已经进入 Stable ID Registry 的 V1 Routine 不批量重命名；Compiler 只对白名单中的历史 ID 放行，新内容必须使用四段式命名。

## Authoring JSON

唯一 Authoring 源仍为：

```text
Content/Routines/routine-templates.json
```

Schema 升级为 `wanhu.routines.v2`，结构：

```json
{
  "id": "routine.work.carpenter.tool-maintenance",
  "category": "work",
  "sourceFacts": ["fact.work.tool-maintenance-completed"],
  "eligibility": {
    "occupations": ["occupation.carpenter"],
    "occupationGroups": [],
    "lifeStages": [],
    "genders": [],
    "weather": []
  },
  "weight": 2,
  "cooldownDays": 10,
  "variants": [
    { "text": "收工前把今天用过的刨子重新磨了一遍。", "weight": 3 },
    { "text": "趁着手头没活，把几件常用工具重新收拾了一遍。", "weight": 2 }
  ]
}
```

`sourceFacts` 表示哪些真实完成事实可以进入这个展示定义。R0 先校验 `fact.*` 命名格式；Fact Registry 与真实 ECS Fact 生产在后续阶段独立落地，不把行为实现写进内容库。

`eligibility` 只负责“谁可以出现”，R0 固定支持 occupations / occupationGroups / lifeStages / genders / weather。没有限制必须写空数组，不省略字段，方便批量内容审查。

`weight` 是多个符合条件 Routine 之间的相对权重；`cooldownDays` 是同一居民再次记录同一 Routine 的最短间隔。没有对应 Fact 时，正式运行时不会因为冷却结束而凭空生成记录。

## Variants

Routine 从 V2 起不再使用单个 `text`，统一使用 `variants[]`。即使当前只有一句，也保留数组。

记录生成时一次性确定 VariantIndex；UI 之后只查表，不在每次打开面板时重新随机。已发布 Variant **只允许末尾追加，不允许重排或删除后复用索引**，否则旧记录的 VariantIndex 会指向另一句话。

文本使用省略主语的第一人称日常记录，例如：

```text
路过早市时买了些家里缺的东西。
午后去井边打了两桶水回来。
收工前把今天用过的工具擦干净了。
晚饭以后在门口坐着乘了一阵凉。
```

不要写成“居民完成了工具维护”这种系统通知，也不要把成婚、添孩子、死亡、搬家、失业等重大结构事件塞进 Routine；这些继续属于 LifeEvent / Fact Chapter。

R0 不开放 `{resident}`、`{place}` 等动态占位符。等 Context Contract 独立设计后再引入，避免素材扩库同时承担实体失效、本地化和存档上下文问题。

## RuntimeIndex 与保存边界

ContentContractCompiler 会输出：

```text
Web/public/generated/routine-catalog-v2.json
```

每个定义增加当前内容构建内的 `runtimeIndex`。Web Demo 的近期记录同时保留：

```text
Routine Stable ID
RuntimeIndex
VariantIndex
Day
```

未来 Unity ECS 热路径可以使用：

```text
RoutineIndex : int
VariantIndex : ushort
Day          : int
Context...   : optional
```

`runtimeIndex` 是**当前内容构建内的稠密索引**，不是跨版本 Stable ID。长期存档必须保存 Stable ID / 内容版本映射，或在加载时通过版本化表完成 remap；禁止把数组下标永久写死后假设后续扩库不会移动。

## 事实与展示分离

目标链保持：

```text
行为 / Schedule / Utility Job
→ ResidentFactEvent
→ ResidentLifeRecordSystem
→ 去重 / 冷却 / eligibility
→ Routine RuntimeIndex + VariantIndex
→ UI Presentation Resolver
```

行为系统只说“发生了什么”，Routine 库只说“这件事是否值得进入近期生活，以及怎样展示”。普通高频节点不直接写 Routine。

## 分阶段生产

```text
R0  契约：命名、JSON、Compiler、RuntimeIndex、VariantIndex、Cooldown、Coverage
R1  泛居民城市日常：家庭、市场、邻里、出行、休闲、公共生活，目标 80～120 个定义
R2  职业日常：当前职业每类先补 8～12 个，再按 Occupation Group 查缺
R3  年龄与家庭：儿童、学生、成年、老人、照料与共同生活
R4  环境变化：天气、昼夜、季节、河道、街巷、市场环境反馈
R5  城市文化与民俗：节令、庙会、社火、茶楼、戏园等
R6  去重与密度审查：近义项、职业覆盖、连续重复、UI 长度、Fact 可触发性
```

每批先看 Coverage 再补缺，不以“句子总数”作为完成标准。

### R1 质量审计

Batch 3 对现有库进行了全量质量审计，并把结果固化为 Compiler 门禁：

- Variant UI 文本最长 24 个 Unicode 字符；当前实际最长 22。
- 全库 Variant 做 NFKC + 空白 / 常用标点归一化后不得重复。
- `sourceFacts` 的顶层域必须与 Routine `category` 一致，例如 `routine.travel.*` 只能由 `fact.travel.*` 进入。
- Coverage 输出最短 / 最长 / 平均文本长度、Fact 数量、Fact 复用清单和分类密度。
- 除 `custom` 外，R1 基线要求每个分类至少 8 个定义；不足会产生 Coverage warning。

R1 收尾审计没有发现重复 Fact、规范化重复文本或超过 24 字的 Variant。R1 的目标不是证明所有 `fact.*` 已在正式 Unity 行为系统实现，而是保证这些 Fact 名称具有明确、可落地的完成语义；正式 Fact Registry 与 ECS 生产仍在后续 Runtime 阶段实现。

### 下一阶段：R2

R2 转为职业专属日常。以当前 15 个 Occupation 为单位，每个职业先做到约 8～12 个具有职业辨识度的 Routine，再按 Occupation Group 看 Coverage。R2 不重写 R1 泛居民条目，也不把职业写死到 Face / Profile 或故事。


## R0 Compiler 门禁

Build 必须拒绝：

- 新 Routine 不符合 `routine.<domain>.<scope>.<action>`；
- category 不在固定列表，或新 ID domain 与 category 不一致；
- sourceFacts 为空、重复或不是 `fact.*`；
- eligibility 引用不存在的 Occupation / Occupation Group，或非法 LifeStage / Gender；
- weight 非正数、cooldownDays 非非负整数；
- variants 为空、文本为空、Variant weight 非正数、单条文本超过 24 字，或跨定义规范化后出现重复文本；
- `sourceFacts` 顶层域与 Routine category 不一致。

`content-coverage.json` 同时输出 Routine 定义数、Variant 总数、各 category 数量和各职业可用 Routine 数量。
