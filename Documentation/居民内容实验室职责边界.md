# 居民内容实验室职责边界

## 项目定位

wanhu-resident-sim 当前职责是《万户天工》的居民内容资产生产、预览、审查与导出工具。

仓库名称保留历史上的 resident-sim，但当前工作不再以“在网页里实现一套居民模拟器”为目标。

这里主要生产和维护：

- Face / Hair / Outfit / Expression 等头像素材与 Catalog；
- 姓名、职业、LifeTag、Resident Profile 等居民定义内容；
- Action Presentation 的显示文本；
- LifeEvent 的短 `recentText`、Story Chapter 的 `memoryText`、Eligibility / Effect 内容定义；
- LifeChapter / 人生经历的展示内容；
- Stable ID、Schema、Reference Validation、Coverage 与 Compiler；
- 固定测试数据下的居民面板、人生时间轴和头像预览。

正式游戏中“居民为什么做一件事、什么时候做、找谁、去哪、是否成功、状态怎样变化”不属于本仓库的算法职责。

---

## 权威分工

### Content / Authoring 是内容权威

本仓库的 Content/、头像 Pack 源资产、Schema 与内容契约负责回答：

~~~text
有哪些内容
这些内容叫什么
Stable ID 是什么
玩家最终看到什么文本 / 素材
内容之间允许引用什么
内容是否完整、可编译、可预览
~~~

例如：

~~~text
resident-action.fetch-water
→ 当前短句“正在井边打水”
→ 最近记录文案若干

lifeevent.child-schooling
→ 一次完整事件正文
→ memoryText（若进入人生经历）
→ Eligibility / Effect 的内容参数
~~~

### Unity 是游戏运行时权威

正式 Unity 主工程负责：

~~~text
Need / Household Need
Schedule
Utility
Behaviour Tree
目标居民 / 地点选择
设施查询
容量与预定
寻路
库存与经济变化
社会关系
行为完成
LifeEvent 触发
结构状态变化
RecentAction 记录算法
LifeChapter 写入时机
ECS / Job / Burst
Save / Load
~~~

具体 ECS Component、Blob、事件容器、并发结构、更新频率、Buffer 容量和算法实现由 Unity 主工程根据真实性能与玩法需求决定。

本仓库可以记录语义边界和内容输入输出，但不提前规定 Unity 的物理实现。

### Web 是内容工作台和预览器

Web 负责：

- 头像编辑与组合预览；
- 居民面板视觉预览；
- RecentAction / RecentLifeEvent 的单句“最近”预览；
- LifeChapter / 人生时间轴与 `memoryText` 深度阅读预览；
- Action Presentation 文案预览；
- 固定 Fixture 下检查文本长度、排版、重复感和可读性；
- DEV 工具帮助人工审查内容。

Web 不负责证明一个行为在真实城市中为何发生。

## 不在 Web 扩张的系统

后续不要继续在 Web 新建或完善：

- Needs；
- Schedule；
- Utility AI；
- Behaviour Tree；
- 朋友 / 家庭 / 社交目标搜索；
- 旅行选择算法；
- affordability / 收入消费模拟；
- 设施容量与预约；
- 导航；
- Household Inventory；
- 城市世界状态模拟；
- 正式 RecentAction RecordSystem；
- 正式 LifeEvent Trigger；
- ECS / Blob / Save 物理布局。

如果某个内容需要这些系统才能真正发生，只记录它的内容契约和展示资产，等 Unity 具备对应能力后再接入。



## 内容生产主链

长期主链固定为：

~~~text
Authoring Content / Avatar Source
            ↓
Schema / Stable ID / Reference Validate
            ↓
Content Compiler
            ↓
Coverage / Lint / Duplicate Review
            ↓
Web Preview / Avatar Workshop / Resident Panel
            ↓
人工审内容与视觉
            ↓
Compiled Content / Export
            ↓
Unity 消费内容资产
~~~

Web Preview 不位于游戏算法链中。

## Action Presentation 边界

Action Presentation 只描述“一个真实行为发生以后，怎样展示给玩家”。

可以包含：

- Stable ID；
- 当前活动短句；
- 少量最近记录 Variant；
- 展示所需的轻量参数。

不要加入用于决定行为是否发生的复杂 Eligibility。

新的 Action Presentation 原则上跟随 Unity 已实现或已经明确排期的 Behaviour 增长，不为了扩大内容数量先编造居民实际上不会执行的行为。

---

## LifeEvent 边界

LifeEvent 是最适合当前仓库持续生产的内容资产之一。

Web 可以验证：

- `recentText` 是否足够短、能在几秒内扫读；
- RecentAction 与 RecentLifeEvent 是否保持一致的信息密度；
- 结构事实 / LifeTag 的后续资格是否合理；
- `memoryText` 是否只服务人生经历并像完整回忆；
- Eligibility / Effect 引用是否合法；
- 同一重要事件是否避免 Fact Chapter / Story Chapter 重复；
- 不同年龄、职业、家庭状态的人生故事覆盖是否失衡。

LifeEvent 不再默认拥有 Stage。长故事拆成多个离散事件，通过结构事实、长期 LifeTag 或少量短期机会 Tag 形成弱关联；禁止用 `story-x-stage-1/2/3` 一类 Tag 重新实现 Stage 状态机。

真正的触发概率、候选选择、世界条件、结构变化提交和运行时状态更新由 Unity 决定。

---

## 头像边界

头像仍是本仓库的正式内容生产能力。

Web 可以继续负责：

- 素材创作；
- Catalog；
- Frame 适配；
- Renderer；
- 编辑器；
- 组合审查；
- 小尺寸可读性；
- Recipe 导入导出与玩家覆盖预览。

Unity 以后消费最终内容和配方语义，不要求复制 Web 编辑器实现。

---

## Review 边界

内容生产需要快速迭代，不应因为改一段故事文本就长期跑完整头像资产回归。

目标 Review 分层应是：

~~~text
文档
→ 不需要视觉回归

LifeEvent / Action / Name / Occupation / Tag / Profile 内容
→ Build + 居民内容专项 Review

头像素材 / Catalog / Renderer
→ Avatar 专项 Review

Resident Panel / Avatar Workshop 交互
→ 对应浏览器 UI Review

跨域基础设施变化
→ 完整回归
~~~

GitHub Actions 已拆为 Resident Content Review 与 Avatar Visual Review。普通 LifeEvent / Action / Name / Occupation / Tag / Profile 内容改动不再承担 8A / 8B / 8D 头像全量回归；只有跨域文件才同时触发两边。
