# 居民内容生产与运行时数据管线 V1

## 目标

本设计用于把当前“居民逻辑网页 Demo”逐步演进成一套可批量生产、可验证、可编译，并能被未来 Unity Runtime 消费的居民内容生产线。

核心原则：

> Web 继续作为玩法与内容原型；正式游戏运行时使用独立的紧凑数据布局。两者共享内容源、Stable ID、字段语义和规则，不共享同一份内存结构。

当前阶段先确定长期契约和实施顺序，不要求一次完成所有 Compiler、Unity Blob 或资源系统。

---

## 1. 四层数据模型

居民系统分成四层：

```text
Authoring Data
人工维护内容
        ↓
Resident Content Compiler
校验 / 引用解析 / StableId / Bucket / Coverage
        ↓
Compiled Content
├─ Web Demo Bundle
└─ Unity ResidentContentBlob
        ↓
Runtime State / Save Data
```

### Authoring Data

给人和 AI 编辑的内容源，强调：

- 可读
- 可审查
- 可批量生产
- Git diff 清晰
- 不为 Runtime 内存布局妥协

### Compiler

唯一负责把 Authoring 转换为运行时可消费数据的层。

### Compiled Content

只读定义数据。Web 与 Unity 可以输出不同格式，但内容语义必须一致。

### Runtime State / Save

只保存某个居民“实际发生了什么”和“现在是什么状态”，不复制 Definition 文本和资源描述。

## 2. Web Demo 的明确定位

Web Demo 继续负责验证：

```text
Resident Panel 是否好用
LifeEvent 是否自然
人生时间轴是否有代入感
故事文本是否适合真实 UI
年龄 / 家庭 / 职业条件是否合理
城市变化是否能反馈到个人
```

Web Demo 可以继续使用：

- JSON
- 字符串 ID
- `displayName`
- `portraitSeed`
- 固定 CitySeed Snapshot
- DEV 面板
- 快速推进时间

这些是原型工具，不代表正式 Runtime 必须保存相同字段。

## 4. Stable ID 规则

显示文本和数组位置都不能充当长期身份。

推荐 Stable ID：

```text
occupation.carpenter
life.service.draft
life.work.carpenter.first_independent_job
name.surname.lu
name.given.mingyuan
lifetag.served_military
portrait.hair.017
```

规则：

- ID 一旦进入正式内容和存档，不因显示名修改而变化。
- Authoring 允许字符串 Stable ID。
- Compiler 可以把 Stable ID 编译成 `uint` hash 或紧凑 RuntimeIndex。
- Save 不长期保存易变数组位置。
- 加载存档时由 StableId / StableIdHash 解析当前 RuntimeIndex。

这样未来增加、删除、重新排序 Definition 时，不会让旧存档整体错位。

## 5. Name V2

### 5.1 不做随机汉字笛卡尔组合

Given Name 以人工审核过的完整 token 为主：

```text
明远
景和
仲平
静和
知微
素秋
```

而不是默认：

```text
明 + 远
清 + 平
```

任意拼接。

### 5.2 Authoring 目标

```json
{
  "id": "name.given.mingyuan",
  "text": "明远",
  "gender": "male",
  "weight": 5,
  "generationGroups": ["middle", "young"],
  "styles": ["plain", "literary"]
}
```

姓氏同样有稳定 ID 和权重：

```json
{
  "id": "name.surname.lu",
  "text": "陆",
  "weight": 30
}
```

### 5.3 家庭先于姓名成员生成

推荐流程：

```text
Generate Household
↓
Resolve Household Surname Rule
↓
Generate Members
```

默认：

- 子女通常继承家庭姓氏。
- 配偶保留自己的原姓。
- 特殊情况以后通过规则扩展。

姓名允许重复，不做全城唯一检测。

### 5.4 规模目标

第一轮正式内容可以逐步达到：

```text
姓氏           100～150
男性 Given     300～500
女性 Given     300～500
通用 Given     100～200
```

无需一次补齐，Compiler Coverage 可以持续提示池子不足。

## 6. LifeTag / Story Anchor

LifeTag 是过去经历的紧凑事实，不是玩家成就。

例如：

```text
lifetag.served_military
lifetag.trained_carpenter
lifetag.opened_shop
lifetag.debt_history
lifetag.migrated
lifetag.widowed
lifetag.learned_medicine
```

用途：

```text
过去 Story
↓
Add LifeTag
↓
几年后 StorySelector
↓
requiredTags / forbiddenTags
```

正式 Runtime 可把常用 LifeTag 编译为 bitset；少数扩展标签也可以使用紧凑索引。

Story 选择时不扫描历史长文本。

---

## 7. LifeEvent Authoring 目标

当前 LifeEvent V2 的核心继续保留：

```text
id
weight
eligibility
source
recordToHistory
stages
```

后续分阶段增加两类能力：

### 7.1 Tag Eligibility

```json
{
  "requiredTags": ["lifetag.trained_carpenter"],
  "forbiddenTags": ["lifetag.opened_shop"]
}
```

### 7.2 Effects

```json
{
  "effects": [
    {
      "type": "addTag",
      "tag": "lifetag.opened_shop"
    }
  ]
}
```

Effect 只描述结果，不直接绑定某个 Unity 系统实现。

建议支持的效果类别逐步增加：

```text
AddLifeTag
RemoveLifeTag
SetStateBit
ClearStateBit
ChangeOccupation
ChangeWorkplace
MoveHousehold
Marriage
BirthChild
AddLifeChapter
```

其中会修改多个实体的结构变化，在 Unity Runtime 中必须转成集中结构 Request / Command，不在 Resident 并行 Job 内直接改多个 Entity。

## 8. Story Bucket

内容规模扩大后不能让每个居民每次更新扫描全部 LifeEvent。

Compiler 需要按粗粒度条件预建候选 Bucket：

```text
AgeStage
+
Occupation / OccupationGroup
+
Story Domain
↓
StoryBucket
```

例如：

```text
青年
├─ 通用
├─ 工匠
├─ 医疗
├─ 商贸
├─ 家庭
└─ 城市
```

Runtime 再针对几十条候选做：

```text
LifeTag
Family State
Resident State
World Snapshot
```

过滤和加权抽取。

目标是让内容数量从几十条增长到几千条时，单个居民更新成本仍然稳定。

## 9. Occupation 数据

Occupation 不只是显示名，还要成为 Story Bucket 和 Activity 的稳定分类入口。

目标 Authoring：

```json
{
  "id": "occupation.carpenter",
  "name": "木工",
  "groups": ["craft"],
  "workplaceTypes": ["carpenter_shop", "construction_site"],
  "minAge": 14,
  "maxAge": 70,
  "workActivityPool": [],
  "offActivityPool": [],
  "storyGroups": ["craft", "construction"]
}
```

职业组示例：

```text
craft
medical
trade
official
labor
agriculture
transport
education
```

这样很多故事可以针对 `craft`，而不是逐个列出木工、铁匠、石匠。

## 10. RecentAction 的正式 Runtime 方向

近期展示不再拥有独立行为生成系统。

正式方向是：

```text
Behaviour Complete
→ ResidentActionCompletedEvent
→ RecentActionRecordSystem
→ RecentAction 小环
```

Action Presentation 只负责文本展示和轻量记录策略，不决定行为 Eligibility。目标居民、地点和设施上下文由 Behaviour 本身提供。

最近记录可以作为小型 Save 数据保留，但只保存 Day、ActionType / StableId Mapping、VariantIndex 和必要 Target / Place，不保存文本，也不保存完整行为轨迹。

## 11. Appearance / Portrait

### 11.1 Seed 与稳定外观分离

`PortraitSeed` 可以用于第一次生成。

但是正式存档不能每次根据当前资源池重新随机，因为添加新发型后可能导致老居民外观改变。

因此正式 Runtime 保存 `AppearanceDNA`。

### 11.2 AppearanceDNA 目标

```text
FaceId
HairId
BrowId
BeardId
HeadwearId
OutfitId
SkinPalette
HairPalette
ClothingPalette
FeatureFlags
```

字段使用紧凑整数索引或 StableIdHash 的编译结果。

### 11.3 UI 和 3D 共享识别特征

UI Portrait 与世界 3D Character 至少共享：

```text
性别
年龄阶段
肤色
发色
发型类别
胡须
帽子 / 头饰
职业服饰类别
```

不要求 UI 头像和 3D 五官逐像素一致，但玩家识别出的核心特征必须一致。

### 11.4 按需头像缓存

不为几千居民长期持有 RenderTexture。

推荐：

```text
打开居民面板
↓
Portrait Cache Lookup
├─ Hit  → Display
└─ Miss → Compose / Render → Cache
```

缓存容量以后根据真实平台测试确定。

```text

stories.json

```

### Unity ResidentContentBlob

正式 Unity 只读数据大致包含：

├─ ActionPresentations
├─ LifeEvents
├─ LifeTags
├─ LifeStages

├─ TextTable

## 13. ECS Runtime 目标

Web 当前 `ResidentRecord` 是 Demo DTO，不是最终 ECS Component。

正式方向按 Hot / Cold 分离：

### Identity

```text
ResidentIdentity
├─ ResidentId
├─ Seed
├─ BirthDay
├─ SurnameId
├─ GivenNameId
└─ Gender
```

### Simulation State

```text
ResidentSimulationState
├─ OccupationIndex
├─ WorkplaceId
├─ HouseholdId
├─ NextUpdateDay
├─ StateBits
└─ LifeTagBits
```

### Appearance

```text
ResidentAppearance
└─ AppearanceDNA
```

### Buffers / Cold Data

```text
DynamicBuffer<ResidentStoryThread>
DynamicBuffer<ResidentLifeChapter>
```

不把故事正文、姓名字符串、职业显示名、Action Presentation 文本复制到 Entity。

## 14. Life Chapter 存储

一个故事章节只需要保存紧凑事实：

```text
Day
EventStableId / RuntimeIndex
Variant / Outcome
Optional Payload
```

例如：

```text
27岁 · 被征去服役
```

Resident 实例不保存完整三阶段正文。

UI 展开时：

```text
ResidentLifeChapter
↓
Event ID
↓
ResidentContentBlob
↓
TextTable
↓
显示完整故事
```

事实型 Chapter，如结婚、换工，也可以保存专门的 Chapter Type + 参数，而不伪造 Story 文本。

## 15. Save Data 原则

正式 Save 长期保存的应是：

```text
ResidentId
Seed
BirthDay
Gender
SurnameId
GivenNameId
AppearanceDNA
Occupation StableId / Index Mapping
WorkplaceId
HouseholdId
StateBits
LifeTagBits
NextUpdateDay
StoryThread[]
LifeChapter[]
```

不保存：

```text
完整姓名字符串
职业显示名
故事正文
故事标题
Action Presentation 文本
头像图片
```

这些全部由当前 Content Database 提供。

## 16. Coverage Matrix

批量生产不能只看“总共写了多少条”。

Compiler 后续输出 Coverage，例如：

```text
              少年  青年  壮年  中年  晚年
通用           42    63    54    31    26
家庭           18    51    77    61    38
工匠           31    46    58    41    22
商贸            8    27    52    37    19
医疗            4    13    21    16     8
```

还应统计：

- 性别相关题材覆盖
- 婚姻 / 未婚 / 有子女 / 无子女
- 不同职业组
- 不同人生阶段
- `recordToHistory` 比例
- Source 类型
- Required / Forbidden Tag 使用情况
- 永远无法命中的事件
- 重复 Stable ID
- 缺失引用

以后 AI 批量内容任务应从 Coverage 缺口出发，例如：

> 补“青年 × 医疗 × 家庭”20 条。

## 17. Compiler 最终职责

Resident Content Compiler 目标流程：

```text
Load Authoring
↓
Schema Validate
↓
Reference Validate
↓
Content Lint
↓
Stable ID Compile
↓
Story Bucket Build
↓
Text / Asset Table Build
↓
Coverage Analyze
↓
Export
├─ Web Demo Bundle
└─ Unity Blob / Intermediate
```

`Parser / Validator / Compiler / Exporter` 分工清楚，不让 Web 页面承担内容编译职责。

## 18. 分阶段实施计划

### 阶段 1：数据契约

先做：

- Stable ID 规则
- LifeTag Registry
- Name V2 Authoring
- Occupation V2 Authoring
- LifeEvent 条件 / Effect 目标契约
- Portrait Catalog / AppearanceDNA 契约

本阶段主要修改文档、Schema 和小型 Validator，不改变核心玩法。

### 阶段 2：Content Compiler

实现：

- 统一加载 Authoring
- 引用检查
- StableId 编译
- Story Bucket
- Coverage Report
- Web Demo Bundle

### 阶段 3：Web Demo 迁移

Web 仍是原型，但逐步做到：

> 只消费 Compiler 输出，不自己发明另一套内容规则。

继续用 Demo 快速验证玩法和内容。

### 阶段 4：Unity Runtime Contract

在正式游戏仓库实现：

- `ResidentContentBlob`
- ECS Hot / Cold Components
- StoryThread / LifeChapter Buffer
- Save StableId Mapping
- 集中 Structural Request

本阶段不要直接复制 Web `ResidentRecord`。

### 阶段 5：批量生产

生产线稳定后再扩：

- 数百到数千 LifeEvent
- 大姓名池
- Portrait Parts / 3D 外观资源
- Resident Behaviour 对应的 Action Presentation 内容

内容生产始终由 Coverage 驱动。

---

## 19. 当前阶段的验收标准

现在只要求：

1. Web Demo 继续可运行，并可由 GitHub Actions 在本地 Vite 环境中自动截图审查。
2. 文档明确 Web Demo 与正式 Runtime 的边界。
3. Build 能独立编译并上传当前 generated Demo 数据。
4. 后续每一步都有清晰的小目标，不在一次改动中同时重写内容库、Compiler、Web 和 Unity Runtime。

Resident Action Life 基线已经完成；后续内容生产只为真实 Behaviour 提供薄 Presentation，并继续推进 Unity Runtime 契约。
