# 居民内容生产与运行时数据管线 V1

## 目标

本设计用于把当前“居民逻辑网页 Demo”逐步演进成一套可批量生产、可验证、可编译，并能被未来 Unity Runtime 消费的居民内容生产线。

核心原则：

> Web 当前作为居民内容实验室与预览器；正式游戏算法只在 Unity 主工程实现。两边共享内容源、Stable ID 与必要语义，不共享游戏决策代码，也不要求使用相同的数据结构。

当前阶段先确定长期契约和实施顺序，不要求一次完成所有 Compiler、Unity Blob 或资源系统。

---

## 1. 四层数据模型

居民系统分成四层：

```text
Authoring Data
人工维护内容
        ↓
Resident Content Compiler
校验 / 引用解析 / StableId / Bucket / Coverage
        ↓
Compiled Content
├─ Web Preview Bundle
└─ Unity ResidentContentBlob
        ↓
Runtime State / Save Data
```

### Authoring Data

给人和 AI 编辑的内容源，强调：

- 可读
- 可审查
- 可批量生产
- Git diff 清晰
- 不为 Runtime 内存布局妥协

### Compiler

唯一负责把 Authoring 转换为运行时可消费数据的层。

### Compiled Content

只读定义数据。Web 与 Unity 可以输出不同格式，但内容语义必须一致。

### Runtime State / Save

只保存某个居民“实际发生了什么”和“现在是什么状态”，不复制 Definition 文本和资源描述。

---

## 2. Resident Content Lab 的明确定位

Web 负责验证和生产：

~~~text
头像素材与组合
Resident Panel 阅读体验
Action Presentation 短句
LifeEvent recentText 短句
memoryText / Life History 长故事
内容引用与 Coverage
固定 Fixture 下的 UI 密度
~~~

Web 可以继续使用 JSON、字符串 ID、固定 Snapshot、DEV 面板和快速切换样本，但这些只用于内容与 UI 预览。

Web 不实现正式 Need、Schedule、Utility、Behaviour、目标搜索、预约、导航、经济、社会关系、LifeEvent Trigger、RecentAction RecordSystem 或 Save。

Unity 如何消费 Compiled Content、如何组织 ECS / Blob / Buffer，由 Unity 主工程单独决定。本文件中的 Runtime 结构只表达内容与状态应分离等长期原则，不是本仓库下一步要实现的代码任务。

## 4. Stable ID 规则

显示文本和数组位置都不能充当长期身份。

推荐 Stable ID：

```text
occupation.carpenter
life.service.draft
life.work.carpenter.first_independent_job
name.surname.lu
name.given.mingyuan
lifetag.served_military
portrait.hair.017
```

规则：

- ID 一旦进入正式内容和存档，不因显示名修改而变化。
- Authoring 允许字符串 Stable ID。
- Compiler 可以把 Stable ID 编译成 `uint` hash 或紧凑 RuntimeIndex。
- Save 不长期保存易变数组位置。
- 加载存档时由 StableId / StableIdHash 解析当前 RuntimeIndex。

这样未来增加、删除、重新排序 Definition 时，不会让旧存档整体错位。

## 5. Name V2

### 5.1 不做随机汉字笛卡尔组合

Given Name 以人工审核过的完整 token 为主：

```text
明远
景和
仲平
静和
知微
素秋
```

而不是默认：

```text
明 + 远
清 + 平
```

任意拼接。

### 5.2 Authoring 目标

```json
{
  "id": "name.given.mingyuan",
  "text": "明远",
  "gender": "male",
  "weight": 5,
  "generationGroups": ["middle", "young"],
  "styles": ["plain", "literary"]
}
```

姓氏同样有稳定 ID 和权重：

```json
{
  "id": "name.surname.lu",
  "text": "陆",
  "weight": 30
}
```

### 5.3 家庭先于姓名成员生成

推荐流程：

```text
Generate Household
↓
Resolve Household Surname Rule
↓
Generate Members
```

默认：

- 子女通常继承家庭姓氏。
- 配偶保留自己的原姓。
- 特殊情况以后通过规则扩展。

姓名允许重复，不做全城唯一检测。

### 5.4 规模目标

第一轮正式内容可以逐步达到：

```text
姓氏           100～150
男性 Given     300～500
女性 Given     300～500
通用 Given     100～200
```

无需一次补齐，Compiler Coverage 可以持续提示池子不足。

## 6. LifeTag / Story Anchor

LifeTag 是过去经历的紧凑事实，不是玩家成就。

例如：

```text
lifetag.served_military
lifetag.trained_carpenter
lifetag.opened_shop
lifetag.debt_history
lifetag.migrated
lifetag.widowed
lifetag.learned_medicine
```

用途：

```text
过去 Story
↓
Add LifeTag
↓
几年后 StorySelector
↓
requiredTags / forbiddenTags
```

正式 Runtime 可把常用 LifeTag 编译为 bitset；少数扩展标签也可以使用紧凑索引。

Story 选择时不扫描历史长文本。

---

## 7. LifeEvent Authoring 目标

当前 LifeEvent V3 的目标 Authoring：

```text
id
title
recentText
weight
eligibility
source
effects?
recordToHistory
memoryText?
```

文本职责固定分层：

```text
recentText
→ 最近
→ 一句短记录

memoryText
→ Story Chapter
→ 人生经历长故事
```

如果内容只是已存在 Behaviour 的完成事实，优先补 Action Presentation，不重复建立 LifeEvent。

当前 main 的 `text` 是过渡字段；下一代码批次迁移到 `recentText`，不保留兼容双轨。

### 7.1 Tag Eligibility

```json
{
  "requiredTags": ["lifetag.trained-carpenter"],
  "forbiddenTags": ["lifetag.opened-shop"]
}
```

### 7.2 Effects

Effect 只描述事件发生后的结果，不直接绑定某个 Unity 系统实现。

现有语义包括：

```text
AddLifeTag
RemoveLifeTag
ChangeOccupation
MoveHousehold
Marriage
BirthChild
LifeChapter
```

会修改多个实体的结构变化，在 Unity Runtime 中必须转成集中结构 Request / Command，不在 Resident 并行 Job 内直接改多个 Entity。

故事连续性链：

```text
结构事实 / LifeTag / 年龄 / 职业 / 世界条件
→ 决定 LifeEvent 是否有资格发生
→ 事件真正发生
→ recentText 写入近期记录
→ recordToHistory?
   ├─ false → 只保留近期记录
   └─ true  → 写入 LifeChapter，读取 memoryText
```

打开人生经历页面时只读取已经发生的 LifeChapter，不扫描当前 Tag 重新生成过去。

## 8. Story Bucket

内容规模扩大后不能让每个居民每次更新扫描全部 LifeEvent。

Compiler 需要按粗粒度条件预建候选 Bucket：

```text
AgeStage
+
Occupation / OccupationGroup
+
Story Domain
↓
StoryBucket
```

例如：

```text
青年
├─ 通用
├─ 工匠
├─ 医疗
├─ 商贸
├─ 家庭
└─ 城市
```

Runtime 再针对几十条候选做：

```text
LifeTag
Family State
Resident State
World Snapshot
```

过滤和加权抽取。

目标是让内容数量从几十条增长到几千条时，单个居民更新成本仍然稳定。

## 9. Occupation 数据

Occupation 不只是显示名，还要成为 Story Bucket 和 Activity 的稳定分类入口。

目标 Authoring：

```json
{
  "id": "occupation.carpenter",
  "name": "木工",
  "groups": ["craft"],
  "workplaceTypes": ["carpenter_shop", "construction_site"],
  "minAge": 14,
  "maxAge": 70,
  "workActivityPool": [],
  "offActivityPool": [],
  "storyGroups": ["craft", "construction"]
}
```

职业组示例：

```text
craft
medical
trade
official
labor
agriculture
transport
education
```

这样很多故事可以针对 `craft`，而不是逐个列出木工、铁匠、石匠。

## 10. RecentAction 的正式 Runtime 方向

近期展示不再拥有独立行为生成系统。

正式方向是：

```text
Behaviour Complete
→ ResidentActionCompletedEvent
→ RecentActionRecordSystem
→ RecentAction 小环
```

Action Presentation 只负责文本展示和轻量记录策略，不决定行为 Eligibility。目标居民、地点和设施上下文由 Behaviour 本身提供。

最近记录可以作为小型 Save 数据保留，但只保存 Day、ActionType / StableId Mapping、VariantIndex 和必要 Target / Place，不保存文本，也不保存完整行为轨迹。

## 11. Appearance / Portrait

### 11.1 Seed 与稳定外观分离

`PortraitSeed` 可以用于第一次生成。

但是正式存档不能每次根据当前资源池重新随机，因为添加新发型后可能导致老居民外观改变。

因此正式 Runtime 保存 `AppearanceDNA`。

### 11.2 AppearanceDNA 目标

```text
FaceId
HairId
BrowId
BeardId
HeadwearId
OutfitId
SkinPalette
HairPalette
ClothingPalette
FeatureFlags
```

字段使用紧凑整数索引或 StableIdHash 的编译结果。

### 11.3 UI 和 3D 共享识别特征

UI Portrait 与世界 3D Character 至少共享：

```text
性别
年龄阶段
肤色
发色
发型类别
胡须
帽子 / 头饰
职业服饰类别
```

不要求 UI 头像和 3D 五官逐像素一致，但玩家识别出的核心特征必须一致。

### 11.4 按需头像缓存

不为几千居民长期持有 RenderTexture。

推荐：

```text
打开居民面板
↓
Portrait Cache Lookup
├─ Hit  → Display
└─ Miss → Compose / Render → Cache
```

缓存容量以后根据真实平台测试确定。

### Identity

```text

├─ ResidentId
├─ Seed
├─ BirthDay
├─ SurnameId
├─ GivenNameId
└─ Gender
```

### Simulation State

```text
ResidentSimulationState
├─ OccupationIndex

├─ NextUpdateDay
```

## 14. Life Chapter 存储

一个故事章节只需要保存紧凑事实：

```text
Day
EventStableId / RuntimeIndex
Variant / Outcome
Optional Payload
```

例如：

```text
27岁 · 被征去服役
```

Resident 实例不保存 LifeEvent 展示正文；UI 通过 Event ID 回查内容定义。

UI 展开时：

```text
ResidentLifeChapter
↓
Event ID
↓
ResidentContentBlob
↓
TextTable
↓
显示完整故事
```

事实型 Chapter，如结婚、换工，也可以保存专门的 Chapter Type + 参数，而不伪造 Story 文本。

## 16. Coverage Matrix

批量生产不能只看“总共写了多少条”。

Compiler 后续输出 Coverage，例如：

```text
              少年  青年  壮年  中年  晚年
通用           42    63    54    31    26
家庭           18    51    77    61    38
工匠           31    46    58    41    22
商贸            8    27    52    37    19
医疗            4    13    21    16     8
```

还应统计：

- 性别相关题材覆盖
- 婚姻 / 未婚 / 有子女 / 无子女
- 不同职业组
- 不同人生阶段
- `recordToHistory` 比例
- Source 类型
- Required / Forbidden Tag 使用情况
- 永远无法命中的事件
- 重复 Stable ID
- 缺失引用

以后 AI 批量内容任务应从 Coverage 缺口出发，例如：

> 补“青年 × 医疗 × 家庭”20 条。

## 17. Compiler 最终职责

Resident Content Compiler 目标流程：

```text
Load Authoring
↓
Schema Validate
↓
Reference Validate
↓
Content Lint
↓
Stable ID Compile
↓
Story Bucket Build
↓
Text / Asset Table Build
↓
Coverage Analyze
↓
Export
├─ Web Preview Bundle
└─ Unity Blob / Intermediate
```

`Parser / Validator / Compiler / Exporter` 分工清楚，不让 Web 页面承担内容编译职责。

## 18. 分阶段实施计划

### 阶段 1：数据契约

已建立 Stable ID、Name、LifeTag、Occupation、LifeEvent、Action Presentation 与头像内容契约。

### 阶段 2：Content Compiler

已建立 Authoring 加载、引用检查、Stable ID、Story Bucket、Coverage 与 Web Bundle 基础能力。

### 阶段 3：Web Content Lab

Web 只消费编译结果并承担内容预览、头像编辑与人工审查，不再发展独立居民模拟规则。

现有 ResidentGenerator / Action Trace / RecordPolicy 只作为固定 Fixture 保留。

### 阶段 4：Unity Runtime

需要正式接入游戏时，在 Unity 主工程根据真实 Behaviour、ECS、Job、性能和 Save 需求实现。

本仓库只提供 Compiled Content 与必要语义文档，不提前完成 Unity Runtime Contract 的物理设计。

### 阶段 5：Recent / LifeChapter 分层与内容生产

LifeEvent V3、Stage 移除和统一“最近”已经完成。

当前先修正展示密度：

- 当前 `text` → 短 `recentText`；
- “最近”每项只显示时间 + 一句话；
- 不在“最近”显示 title + 长正文；
- `memoryText` 只在人生经历展开；
- Tag / 结构事实负责未来故事 Eligibility；
- 故事真正发生后写入 LifeChapter，打开 UI 时不即时重算过去；
- 不保留 `text` / `recentText` 双轨兼容。

修正完成后内容生产分成两条线：

- **Recent 内容**：Action Presentation / recentText，追求高频、短、可扫读；
- **Life History 内容**：Fact Chapter / recordable LifeEvent / memoryText，追求低频、稀疏、有连续性。

内容生产由 Coverage、实际 UI 阅读和玩家体验驱动，不以单纯总条数为目标。

---

## 19. 当前阶段的验收标准

现在只要求：

1. Resident Content Lab 继续可运行，并可在固定 Fixture 下预览居民内容与头像。
2. 文档明确 Content / Web Preview / Unity Runtime 的权威边界。
3. Build 能独立编译并上传当前 generated preview 数据。
4. 后续每一步都有清晰的小目标，不在一次改动中同时重写内容库、Compiler、Web 和 Unity Runtime。

Resident Action Life 与 LifeEvent V3 基线已经足够。当前下一项工程工作是 Recent / LifeChapter 展示语义收敛；完成后再恢复 Recent 短句与 Life History 故事的独立小批量生产。
