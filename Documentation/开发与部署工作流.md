# 开发与部署工作流

## 目标

本仓库现在同时验证两条线：

1. **Web Prototype**：玩法、UI、故事阅读和交互体验。
2. **Resident Content Pipeline**：Authoring 数据、Schema、Compiler、Coverage 与未来 Unity Export。

两条线共享同一仓库和内容源，但验收标准不同。Web Demo 不是正式 Runtime 数据结构；Content Pipeline 也不能为了兼容当前网页 DTO 而锁死未来 Unity ECS。

---

## 1. 分支工作流

继续使用临时分支：

```text
确定本轮目标
    ↓
从最新 main 创建 tmp-* 分支
    ↓
集中修改
    ↓
GitHub Build
    ↓
按改动类型检查 Artifact / Visual Review / Preview
    ↓
继续在同一 tmp-* 修正
    ↓
确认本轮结果
    ↓
重新读取最新 main SHA
    ↓
fast-forward / 合并完整批次
    ↓
main 再跑 Build / Visual Review
```

建议命名：

```text
# Web 玩法 / UI
tmp-prototype-life-history
tmp-prototype-resident-panel

# 内容数据 / Schema / Compiler
tmp-content-name-v2
tmp-content-lifetag-registry
tmp-content-story-buckets

# Runtime Contract 文档 / 中间格式
tmp-runtime-resident-blob
tmp-runtime-save-contract
```

不要求严格按前缀分类，但名字应让人一眼知道本轮目标。

## 2. 当前 GitHub Build

`.github/workflows/validate.yml` 支持：

- `main`
- `tmp-*`
- 指向 `main` 的 Pull Request
- `workflow_dispatch`

Build 现在明确分成：

```text
Install dependencies
↓
Compile resident demo content
↓
Upload resident-generated-data Artifact
↓
Build Web Prototype
```

### Compile resident demo content

当前执行：

```bash
npm run build-content
```

负责现有：

```text
StoryCompiler
ResidentGenerator
LifeEventCompiler
```

本阶段输出仍然是 Web Demo Bundle，不代表未来 Unity Runtime 格式。

### resident-generated-data Artifact

Build 上传：

```text
Web/public/generated/stories.json
Web/public/generated/definitions.json
Web/public/generated/resident-snapshot.json
```

作用：

- 不打开网页也能检查 Compiler 输出。
- Schema / 内容逻辑改动可以单独审查 generated 数据。
- 后续加入 `coverage.json`、StableId registry、Unity intermediate 时，可以继续扩展这个 Artifact 或拆成独立 Artifact。

### Build Web Prototype

当前执行：

```bash
npm run build -w Web
```

只负责 TypeScript / Vite Web 构建。

这样可以明确区分：

```text
内容编译失败
≠
Web UI 构建失败
```

## 3. Resident Visual Review

`.github/workflows/visual-review.yml` 继续服务 Web Prototype。

流程：

```text
安装依赖与中文字体
↓
Build generated content
↓
启动本地 Vite
↓
Playwright 打开真实页面
↓
抓取居民面板 / LifeEvent / 人生模式 / DEV 画面
↓
压缩 WebP
↓
上传 resident-visual-review
```

### 什么时候 Visual Review 是主验收

适用于：

- Resident Panel 布局
- 颜色 / 字体 / 间距
- 人生模式
- LifeEvent 阅读体验
- 交互层级

### 什么时候 Generated Artifact 是主验收

适用于：

- Name / Occupation / LifeTag Schema
- Compiler
- Stable ID
- Story Bucket
- Coverage
- Snapshot 生成逻辑

数据改动即使没有视觉变化，也必须通过 Build。Visual Review 可以继续自动运行，但不是数据契约的权威验证方式。

---

## 4. Vercel Preview / Production

Vercel 从仓库根目录构建：

```text
Build Command: npm run build
Output Directory: Web/dist
```

分支关系：

```text
tmp-* → Vercel Preview
main  → Vercel Production
```

Preview 主要用于：

- 鼠标交互
- 展开 / 收起
- 切换居民
- 推进故事
- 人生时间轴体验

数据 Schema / Compiler 改动不应该只凭 Preview 判断正确性。

如果 Vercel 发生 deployment/build rate limit，不连续推空 commit；继续依赖 GitHub Build、generated Artifact 和 Visual Review。

## 5. 两条实施路线

### A. Web Prototype 路线

```text
Content / compiled demo data
↓
Web Prototype
↓
Playtest
↓
确认玩法规则
↓
把稳定规则写回长期文档 / Schema
```

Web 可以快速试错，允许暂时性的 DEV 字段和验证数据。

### B. Content Pipeline 路线

```text
Authoring Contract
↓
Schema / Validator
↓
Stable ID / Reference Resolve
↓
Compiler
↓
Coverage
↓
Web Bundle
↓
未来 Unity Blob / Intermediate
```

Pipeline 的规则一旦稳定，应尽量保持向后兼容，特别是进入 Save 的 Stable ID。

## 6. 分阶段 Gate

### 阶段 1：数据契约

目标：

- Stable ID 规则
- LifeTag Registry
- Name V2
- Occupation V2
- LifeEvent Effects / Tag 条件契约
- Portrait Catalog / AppearanceDNA 契约

验收：

- 文档一致
- Schema / 小型 Validator 可运行
- 不要求 Unity Exporter

### 阶段 2：Content Compiler

目标：

- 统一加载 Authoring
- 引用检查
- StableId 编译
- Story Bucket
- Coverage Report
- Web Bundle

验收：

- Build 能明确失败在错误内容
- generated Artifact 包含可检查报告
- 同一输入稳定生成同一输出

### 阶段 3：Web Demo 迁移

目标：

- Web 只消费 Compiler 输出
- 不在组件里重新定义 Story / Name / Occupation 规则

验收：

- 原型玩法不退化
- Visual Review / Preview 继续工作

### 阶段 4：Unity Runtime Contract

目标：

- ResidentContentBlob
- ECS Hot / Cold
- StoryThread / LifeChapter Buffer
- Save StableId Mapping
- Structural Request

验收：

- 不复制 Web DTO
- Runtime 不解析 JSON / Markdown
- 可用少量测试数据跑通生成 → 更新 → UI 查询

### 阶段 5：批量生产

目标：

- 故事、名字、Occupation、Portrait 资源规模化

验收：

- 由 Coverage Matrix 指导生产
- 不只看总条数
- 自动检测重复 ID、缺失引用、永远无法命中的内容

---

## 7. Main 更新规则

自动化助手准备更新 `main` 前必须重新读取 `main` SHA。

禁止：

- 基于过期 main 创建 sibling commit 后强制覆盖。
- 为了触发 Vercel 连续提交空 commit。
- 同一逻辑功能按“一个文件一个 commit”推进 main。

临时分支允许中间调试 commit；进入 main 时尽量保留一个逻辑完整批次。

---

## 8. 文档 / Schema / Code 同步规则

涉及稳定数据契约时：

```text
设计文档
+
Schema
+
Compiler / Validator
+
Demo 消费代码
```

必须保持字段语义一致。

但不要求所有阶段一次完成。可以先在文档中标记“目标契约 / 尚未实现”，再按阶段补代码；不能把尚未实现的目标写成当前已完成事实。
