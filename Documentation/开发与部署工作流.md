# 开发与部署工作流

## 目标

本仓库的 Web 原型以 GitHub 为代码权威，以 GitHub Actions 为主要构建与视觉验证入口，以 Vercel Production 作为阶段性可交互版本。

开发时可能同时修改 Content、Generator、Schema、Web、脚本与文档。为了避免每个小改动都触发 Production Deployment，后续采用与 `wanhu-ui-prototype` 类似的分支与 Visual Review 流程：

> 迭代放在 `tmp-*` 临时分支；GitHub Actions 在临时分支上完成 Build 和截图验证；确认后再把一个完整逻辑批次推进到 `main`。

`main` 是稳定开发状态；Vercel Production 是 `main` 的线上结果，不反过来决定仓库版本。

---

## 推荐流程

```text
确定本轮目标
    ↓
从最新 main 创建 tmp-* 分支
    ↓
在 tmp-* 上集中修改相关文件
    ↓
GitHub Build
    ↓
Resident Visual Review
    ↓
直接查看压缩后的单张截图
    ↓
继续在 tmp-* 修正
    ↓
确认本轮结果
    ↓
重新读取最新 main，确认没有被其他提交推进
    ↓
整理为一个完整 commit / 合并到 main
    ↓
GitHub Actions 再验证一次
    ↓
Vercel 只部署最终 main
```

推荐临时分支名：

```text
tmp-resident-panel
tmp-life-events
tmp-resident-generator
tmp-ui-density
```

`tmp-*` 分支会运行 GitHub Build 与 Visual Review，但 `vercel.json` 已禁止这些分支触发 Vercel 自动部署，避免 Preview / Production 部署请求消耗额度。

## GitHub Actions

### Build

`.github/workflows/validate.yml` 在以下情况运行：

- `main`
- `tmp-*`
- 指向 `main` 的 Pull Request
- 手动 `workflow_dispatch`

Build 必须至少验证：

```text
StoryCompiler
ResidentGenerator
LifeEventCompiler
TypeScript
Vite Build
```

Build 成功才说明当前代码和内容可以进入下一步。

### Resident Visual Review

`.github/workflows/visual-review.yml` 同样支持 `main` 与 `tmp-*`。

流程：

```text
安装依赖与中文字体
↓
Build generated content
↓
启动本地 Vite
↓
Playwright 以 1920×1080 打开真实页面
↓
抓取玩家居民面板 / 事件推进 / 人生经历 / DEV 密度等画面
↓
压缩为 WebP
↓
上传 resident-visual-review Artifact
```

视觉迭代优先看 Artifact，不要为了每一次字体、间距、信息层级微调都依赖 Vercel Production。

---

## 截图汇报规则

当自动化助手完成 UI Visual Review 后，默认不要只发一个 ZIP。

应当：

1. 下载 `resident-visual-review` Artifact。
2. 解压缩。
3. 直接把关键 WebP 逐张作为可点击链接发给用户。
4. 链接名称说明截图内容，例如：

```text
玩家居民面板
生活事件推进
人生经历展开
DEV 密度检查
```

只有用户明确需要完整包时，才额外提供 ZIP。

## Vercel 策略

Vercel 从仓库根目录构建：

```text
Build Command: npm run build
Output Directory: Web/dist
```

当前 `vercel.json` 禁止 `tmp-*` 自动部署：

```json
{
  "git": {
    "deploymentEnabled": {
      "tmp-*": false
    }
  }
}
```

因此正常开发节奏应当是：

```text
tmp-* → GitHub Actions / 截图审查
main  → GitHub Actions + Vercel Production
```

这样一轮功能通常只需要一次 Production Deployment。

---

## Vercel 是否真的更新：必须比较 Commit SHA

不要仅凭页面看起来像旧版本判断，也不要仅看 Deployment 时间。

正确检查：

```text
GitHub main 当前 SHA
vs
Vercel Production Deployment 显示的 Git SHA
```

两者一致，才代表线上是最新 `main`。

如果不同：

- GitHub `main` 是当前代码状态。
- Vercel 页面仍是旧版本。
- 不需要补部署每一个历史 commit；只需要让最新 `main` 成功部署一次。

如果 GitHub Actions 成功、Vercel 失败，要继续区分：

- TypeScript / Vite 错误：代码构建问题。
- `Deployment rate limited`：部署平台限制，不是代码错误。
- Vercel 正在构建旧 SHA：旧日志不能代表当前 `main`。

---

## Main 更新规则

自动化助手在准备把临时工作推进到 `main` 前，必须重新读取 `main` 当前 SHA。

禁止：

- 基于过期的 main SHA 创建 sibling commit 后强行覆盖 main。
- 为了触发 Vercel 连续提交空 commit。
- 一个文件一个 commit 地推进 main。

如果 `main` 在开发期间已经前进，应先比较 / 合并 / 重放本轮修改，再做 fast-forward 更新；除非用户明确要求，否则不 force rewrite `main`。

---

## 一轮功能的 Commit 原则

一个逻辑功能批次尽量只在稳定分支留下一个完整提交，例如：

```text
Implement resident temporary life state
```

这个提交可以同时包含：

- Content 定义
- Simulation / Generator
- Web UI
- Schema
- Visual Review 脚本
- 长期文档

不要把同一个功能拆成：

```text
Add type
Add helper
Update UI
Fix helper
Fix type
Update docs
Fix build
```

临时分支上允许为了调试保留中间 commit；进入 `main` 时以逻辑完整为优先。

## 当前部署边界

```text
tmp-* branch
    ↓
GitHub Actions
    ├─ Build
    └─ Resident Visual Review

main
    ↓
GitHub Actions
    ├─ Build
    └─ Resident Visual Review
    ↓
Vercel Production
```

这套流程的目的不是追求复杂的 Git Flow，而是让高频 AI / UI 迭代不再制造大量 Production Deployment，同时保证每次 `main` 都是可构建、可截图审查的完整状态。
