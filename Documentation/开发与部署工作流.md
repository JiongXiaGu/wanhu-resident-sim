# 开发与视觉审查工作流

> 文件名沿用历史名称 `开发与部署工作流.md`，但当前流程已经**取消远端部署依赖**。本仓库的远端验收只使用 GitHub Actions Build 与 Resident Visual Review 截图 Artifact。

## 目标

本仓库当前只服务 **Web 玩法原型验证**。

这里继续保留 Authoring、Schema、Compiler、Stable ID、LifeTag、Story Bucket、Coverage、Portrait Catalog 等内容工具，因为它们能帮助批量生产和稳定复现玩法；但不再在本仓库设计 Unity Save、Blob、ECS Runtime Contract、RuntimeIndex 或正式资源加载方案。

当前工作流保证三件事：

1. Web Prototype 可以快速试玩法、UI、故事阅读和交互。
2. Build / 内容契约问题由 GitHub Actions 自动检查。
3. UI / 头像 / 美术结果由 GitHub Actions 在 Runner 内启动本地 Vite、运行 Playwright 并输出截图 Artifact，不需要 Vercel Preview / Production。

---

## 1. 当前唯一远端验收链

一次逻辑开发批次：

```text
确定本轮目标
↓
读取最新 main SHA
↓
从 main 创建 tmp-* 分支
↓
集中完成代码 / 内容 / 文档修改
↓
一次性生成一个聚合 commit
↓
只 push 一次 tmp-*
↓
GitHub Build
+
Resident Visual Review
↓
下载 resident-visual-review Artifact
↓
实际查看关键截图
↓
如有问题：聚合修正后再 push 一个修正 commit
↓
Build / Visual Review / 截图审查都通过
↓
重新读取最新 main SHA
↓
一次推进 main
↓
main 再跑 GitHub Build + Resident Visual Review
```

核心规则：

> **GitHub Actions + 截图 Artifact 是当前唯一远端验收方式。**

本流程不需要：

```text
Vercel Preview
Vercel Production
线上临时站点
等待 Deployment Status
为了刷新网页而提交空 commit
```

---

## 2. 原子批次原则

一个逻辑批次应尽量只产生一个远端 tmp commit。

如果截图或自动检查暴露问题，可以再增加一个**聚合修正 commit**。不要把同一轮工作拆成“一个文件一个 commit”。

推荐：

```text
create_blob
↓
create_tree
↓
create_commit
↓
update_ref
```

或在本地工作树完成全部修改后一次 `git commit` / `git push`。

这样做的目的不是减少部署次数，而是：

- 让每个 Action Run 对应一个可理解的工作批次；
- 方便比较截图前后变化；
- 避免多个未完成状态同时出现在远端；
- 让 main 历史保持清楚。

## 3. 分支命名

玩法 / UI：

```text
tmp-prototype-life-history

tmp-prototype-world-feedback
```

内容 / Schema / Compiler：

```text

```

头像 / 美术：

```text

```

不再使用 `tmp-runtime-*` 作为本仓库下一阶段路线；正式 Unity Runtime 进入 Unity 工程后重新设计。

## 4. GitHub Build

`.github/workflows/validate.yml` 支持：

- `main`
- `tmp-*`
- 指向 `main` 的 Pull Request
- `workflow_dispatch`

当前 Build：

```text
Install dependencies
↓
npm run build-content
↓
Upload resident-generated-data Artifact
↓
npm run build -w Web
```

`build-content` 当前包括：

```text
ContentContractCompiler
↓
PortraitCatalogAudit
↓
StoryCompiler
↓
ResidentGenerator
↓
LifeEventCompiler
↓
StoryBucketCompiler
↓
ResidentSnapshotCompiler
↓
ResidentPortraitCompiler
↓
WebContentCompiler
```

Generated Artifact 主要用于检查：

- Authoring / Schema / Reference 是否一致；
- Stable ID / LifeTag / Occupation Group 是否正确；
- Story Bucket 与 Coverage 是否合理；
- Portrait Catalog / Art Manifest 是否一致；
- Demo Snapshot 是否能稳定生成。

这些 generated JSON 都只是 Web 原型数据，不代表未来 Unity Runtime 或 Save 格式。

## 5. Resident Visual Review

`.github/workflows/visual-review.yml` 是当前 UI / 玩法 / 头像的远端视觉验收入口。

流程：

```text
安装依赖与截图所需字体
↓
Build generated content
↓
在 GitHub Runner 启动本地 Vite
↓
Playwright 打开 localhost 页面
↓
执行真实交互
↓
检查 DOM / 状态变化
↓
抓取关键页面 / 区域截图
↓
压缩为 WebP
↓
上传 resident-visual-review Artifact
```

这意味着：

> **视觉审查不需要把网页部署到公网。**

Visual Review 同时承担两种职责。

### 自动不变量

例如：

- 人生模式隐藏 Activity / 当前 LifeEvent / Routine；
- 人生时间轴年龄顺序正确；
- Prototype Effect 真实改变居民状态；
- LifeTag 能解锁后续故事；
- Portrait Render Contract / Frame 不变量成立；
- Style Bakeoff 的角色数、SVG 数和隔离规则成立。

### 截图审查

例如：

- Resident Panel 整体布局；
- 居民头像近景；
- Face / Hair / Outfit 专项；
- 24 人 Crowd；
- Portrait Style Bakeoff；
- 新增 UI 的关键交互状态。

## 6. CI PASS 与视觉 PASS 不是一回事

对于纯逻辑任务：

```text
Build PASS
+
Resident Visual Review PASS
```

通常可以说明自动验收通过。

对于 UI / 头像 / 美术任务，必须额外执行：

```text
下载 resident-visual-review Artifact
↓
打开关键截图
↓
检查视觉结果
↓
满意后才允许推进 main
```

Resident Visual Review 的绿色状态只能证明：

- 页面能打开；
- 自动脚本没有报错；
- 规定数量的元素存在；
- 截图成功产生。

它**不能证明**：

- 头像好看；
- UI 比例合理；
- 眼睛自然；
- 服饰美术成立；
- 不存在肉眼可见的重复或拼接感。

因此：

> **CI PASS ≠ 美术 PASS。**

如果截图肉眼仍有问题，就继续在 `tmp-*` 修改。

---

## 7. Screenshot Artifact 使用规则

Resident Visual Review 应尽量为重要任务输出：

```text
整体总览
+
关键局部近景
+
需要比较的状态
+
群体 / 重复率样本
```

自动化助手在完成 UI / 美术任务后，应主动下载最新 Artifact 并把关键截图直接提供给用户，而不是要求用户自己打开网页寻找。

完整截图包可以同时提供，方便进一步审查。

---

## 8. 不再使用远端部署做开发验收

当前仓库开发流程明确取消：

```text
tmp-* → Preview Deployment
main → Production Deployment
```

也不再要求：

- 检查 Vercel Status；
- 等待线上 Preview；
- 为刷新线上版本制造提交；
- 因 deployment rate limit 改变 Git 工作流；
- 用公网部署替代 GitHub Action 截图。

仓库中如果仍存在历史部署配置文件，它们不属于当前开发验收流程。后续任务不要主动创建、刷新或检查部署，除非用户明确重新要求恢复线上部署。

---

## 9. main 更新规则

准备更新 `main` 前必须重新读取最新 `main` SHA。

禁止：

- 基于过期 main 创建 sibling commit 后强制覆盖；
- 同一逻辑功能按“一个文件一个 commit”推进 main；
- 为触发 Actions 或刷新截图提交空 commit。

进入 `main` 的 commit 应代表一个完整、可验收的逻辑批次。

对于在 `tmp-*` 上经历多轮修正的任务，可以在最终推进 main 时把最终 tree 压成一个逻辑完整 commit；不必把每一轮视觉试错历史全部带入 main。

main 更新以后必须再次确认：

```text
Build PASS
Resident Visual Review PASS
```

视觉任务还应下载 main 对应的最新 Artifact，确认截图与临时分支验收结果一致。

---

## 10. 文档 / Schema / Code 同步规则

稳定玩法或内容字段变化时，应同步检查：

```text
玩法文档
+
Schema
+
Compiler / Validator
+
Web 消费代码
+
Build
+
Resident Visual Review
```

不能把旧设计继续写成当前事实。例如：

- 人生页取消年龄阶段分组后，不再写“少年 / 青年 / 壮年分组 UI”；
- 人生故事使用 `memoryText` 后，不再写“历史页展开原始三阶段故事”；
- 本仓库停止 Unity Runtime / Save 设计后，不把它列为下一阶段工作；
- 当前取消远端部署验收后，不再要求 Preview / Production / Deployment Status。

---

## 11. 当前边界

当前远端可以验证：

```text
Web Prototype
├─ Resident Panel 当前生活模式
├─ LifeEvent 三阶段过程
├─ Life Chapter 连续年龄时间轴
├─ memoryText 第一人称回忆
├─ LifeTag 连续故事
├─ Prototype Effect
├─ Family Drawer
├─ Content Compiler / Coverage
├─ Portrait Catalog Audit
├─ Build
└─ Resident Visual Review
   ├─ Playwright 自动交互
   ├─ DOM / 状态断言
   └─ Screenshot Artifact
```

下一步继续围绕玩法体验和视觉质量迭代，不在本仓库扩展 Unity Runtime / Save 设计，也不把远端部署作为验收环节。
