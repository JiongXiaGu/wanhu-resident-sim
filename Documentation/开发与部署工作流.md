# 开发与部署工作流

## 目标

本仓库的 Web 原型由 GitHub `main` 驱动，并由 Vercel 自动部署。开发过程中经常需要同时修改 Content、Generator、Schema、Web 与文档；如果把每个文件修改都作为独立 commit 推到 `main`，会造成大量重复 CI / Vercel 构建，并可能触发部署频率限制。

因此后续统一采用：

> 一个逻辑功能批次，尽量只产生一个进入 `main` 的 commit。

GitHub `main` 是代码状态的权威来源；Vercel Deployment 只是该状态的部署结果，不应反过来决定仓库版本。

---

## 一轮开发的推荐流程

```text
明确本轮目标
    ↓
一次性读取 / 检查相关文件
    ↓
在工作区完成同一逻辑批次的全部修改
    ↓
生成内容 / 构建 / 自动检查
    ↓
集中提交为一个 commit
    ↓
GitHub Actions 验证
    ↓
Vercel 自动部署最新 main
    ↓
需要时运行 Visual Review 截图
```

例如“Resident Generator V2”可能同时涉及：

```text
Content/Simulation/
Content/Occupations/
Tools/ResidentGenerator/
Schemas/
Web/src/
Documentation/
```

这些属于同一个功能批次时，应尽量合并到一个 commit，而不是每改一个文件就推一次 `main`。

---

## Commit 原则

### 应该这样

```text
Implement resident temporary story state
```

一个 commit 内完成：

- 数据定义
- Generator / Simulation 逻辑
- Web 展示
- Schema
- 测试或 Visual Review 脚本
- 对应长期文档

### 避免这样

```text
Add type
Add helper
Update UI
Fix helper
Fix type
Update docs
Fix build
```

如果这些修改本质上属于同一个功能，应在推送 `main` 前整理为一个完整批次。

对自动化助手尤其要求：修改多个仓库文件时，优先使用 Git tree / 单次 commit 的方式一次写入，不要使用“一个文件一次 commit”的方式连续推进 `main`。

---

## 验证顺序

### 1. GitHub Actions 是主要构建验证

每个功能批次进入 `main` 后，首先看 GitHub Actions：

- StoryCompiler / ResidentGenerator 是否成功
- TypeScript 是否通过
- Vite 是否成功构建
- Visual Review 是否成功生成截图

如果 GitHub Actions 的完整 build 成功，而 Vercel 因平台频率限制失败，应把两者区分开：前者代表代码构建状态，后者代表部署服务状态。

### 2. Visual Review 用于 UI 迭代

居民 UI 的视觉验证优先通过 GitHub Actions 的截图 Artifact 完成：

```text
1920×1080 页面
↓
玩家视角
↓
故事推进
↓
往事展开
↓
DEV 密度信息
↓
压缩 WebP Artifact
```

不要为了每一次微调都依赖一次新的 Vercel Production Deployment。

### 3. Vercel 用于阶段性可交互验证

Vercel 更适合在一个功能批次完整以后，检查：

- 真正浏览器交互
- Vercel 构建环境
- 公开 / Production 页面
- 连续点击居民时的整体体验

而不是充当逐文件修改后的编译器。

## Vercel 频率限制处理

如果 Vercel 返回 deployment / build rate limit：

1. 不重复提交空 commit 试图强制触发部署。
2. 不为每一个被跳过的历史 commit 单独补部署。
3. 继续以 GitHub `main` 和 GitHub Actions 为开发依据。
4. 后续修改继续按逻辑批次整理，避免进一步制造大量部署请求。
5. 限制解除后，只需要部署当时最新的 `main`；最新 commit 已经包含之前提交的全部历史修改。

Vercel Deployment 列表可能因此落后于 GitHub `main`，这是正常情况。判断“现在仓库里是什么版本”时，应查看 GitHub `main`；判断“线上正在运行什么版本”时，再查看 Vercel Production Deployment 对应的 commit SHA。

---

## 故障判断

### GitHub build 失败

视为代码 / 内容 / Schema / 类型问题，先修复再继续功能开发。

### GitHub build 成功，Vercel build 报 TypeScript 错误

先核对 Vercel 实际部署的 commit SHA。不要假设它正在构建最新 `main`。

如果 Vercel 构建的是旧 commit，则旧日志不能代表当前代码状态。

### GitHub build 成功，Vercel 显示 rate limit

视为部署平台限制，不视为代码错误。

### Vercel 页面没有出现最新 commit

先检查最新 commit 的 Vercel status。如果请求在创建 Deployment 前就被频率限制拒绝，刷新 Deployment 页面不会自动补出这些历史 commit。

---

## 当前仓库的部署边界

```text
GitHub main
    ↓
GitHub Actions
    ├─ build validation
    └─ visual review artifact

GitHub main
    ↓
Vercel
    └─ Production Web
```

未来如果开发频率继续增加，可以再考虑 Preview Branch、手动 Production Promotion 或更细的 Vercel Ignore Build 策略；在当前阶段先保持流程简单，核心是减少无意义的 `main` commit 与重复 Production Build。
