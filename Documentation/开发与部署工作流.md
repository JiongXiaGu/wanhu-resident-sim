# 开发与部署工作流

## 目标

本仓库当前只服务 **Web 玩法原型验证**。

这里继续保留 Authoring、Schema、Compiler、Stable ID、LifeTag、Story Bucket、Coverage、Portrait Catalog 等内容工具，因为它们能帮助批量生产和稳定复现玩法；但不再在本仓库设计 Unity Save、Blob、ECS Runtime Contract、RuntimeIndex 或正式资源加载方案。

当前工作流要同时保证两件事：

1. Web Prototype 可以快速试玩法、UI、故事阅读和交互。
2. 每次远端 push 尽量只触发一次 Build、Visual Review 和 Vercel Deployment，避免因为“一个文件一个 commit”制造无意义的部署请求。

---

## 1. 原子批次原则

一次逻辑开发批次应当这样完成：

```text
确定本轮目标
↓
读取最新 main SHA
↓
从 main 创建 tmp-* 分支
↓
在一个工作批次里完成代码 / 内容 / 文档修改
↓
一次性生成一个聚合 commit
↓
只 push 一次 tmp-*
↓
GitHub Build + Resident Visual Review + Vercel Preview
↓
玩家 / 自动验收
↓
如需修正：聚合完成后再 push 一个修正 commit
↓
重新读取最新 main SHA
↓
一次推进 main
↓
GitHub Build + Resident Visual Review + Vercel Production
```

核心规则：

> **一个逻辑批次 = 一个远端 tmp commit；一个验收修正轮次 = 一个额外 commit；不要把文件级修改拆成连续远端 push。**

原因是 `tmp-*` 已经允许 Vercel Preview。每一次 push 都可能同时触发 GitHub Actions 和一次新的 Vercel Deployment 请求。

### 推荐实现方式

自动化助手优先使用原子 Git 写入：

```text
create_blob
↓
create_tree
↓
create_commit
↓
update_ref
```

或在本地工作树完成全部修改后一次 `git commit` / `git push`。

不要通过连续 `update_file` 把同一批次拆成多次远端 commit。

## 3. GitHub Build

`.github/workflows/validate.yml` 支持：

- `main`
- `tmp-*`
- 指向 `main` 的 Pull Request
- `workflow_dispatch`

当前 Build：

```text
Install dependencies
↓
npm run build-content
↓
Upload resident-generated-data Artifact
↓
npm run build -w Web
```

`build-content` 当前包括：

```text
ContentContractCompiler
↓
StoryCompiler
↓
ResidentGenerator
↓
LifeEventCompiler
↓
StoryBucketCompiler
↓
ResidentSnapshotCompiler
↓
ResidentPortraitCompiler
↓
WebContentCompiler
```

Generated Artifact 主要用于检查：

- Authoring / Schema / Reference 是否一致；
- Stable ID / LifeTag / Occupation Group 是否正确；
- Story Bucket 与 Coverage 是否合理；
- Demo Snapshot 是否能稳定生成。

这些 generated JSON 都只是 Web 原型数据，不代表未来 Unity Runtime 或 Save 格式。

---

## 4. Resident Visual Review

`.github/workflows/visual-review.yml` 服务真实 Web Prototype 验收。

流程：

```text
安装依赖与中文字体
↓
Build generated content
↓
启动本地 Vite
↓
Playwright 打开真实页面
↓
执行玩法交互
↓
检查 DOM / 状态变化
↓
抓取截图
↓
上传 resident-visual-review
```

Visual Review 不只是截图测试，还应覆盖核心玩法不变量。

当前必须持续验证：

- 人生模式隐藏 Activity / 当前 LifeEvent / Routine；
- 人生时间轴按年龄从小到大；
- 不显示“少年 / 青年 / 壮年”等分组；
- 一个节点只代表一件人生事件；
- Story Chapter 展开显示单一 `memoryText`，不显示“起初 / 后来 / 最后”；
- 成婚等 Prototype Effect 真正改变居民状态；
- LifeTag 能解锁后续故事。

---

## 5. Vercel Preview / Production

仓库根目录 `vercel.json` 当前约定：

```text
Build Command: npm run build
Output Directory: Web/dist
```

分支关系：

```text
tmp-* → Vercel Preview
main  → Vercel Production
```

Preview 用于玩家实际体验：

- 鼠标交互；
- 展开 / 收起；
- 切换居民；
- 推进故事；
- 人生时间轴；
- Prototype Effect 与连续故事。

### Deployment 触发纪律

既然 `tmp-*` 已允许 Preview，就必须把远端 push 当成部署触发器处理。

禁止：

- 一个文件一个 commit 连续推到 `tmp-*`；
- 为了看网页刷新而连续推空 commit；
- 前一次 Build / Visual Review 还没开始就连续覆盖分支；
- 为同一逻辑功能制造多个无意义 Preview。

如果 Vercel 返回 deployment/build rate limit：

- 先检查当前 commit 的 GitHub Vercel Status；
- 不继续制造空 commit；
- GitHub Build / Visual Review 仍作为代码正确性证据；
- 下一次确实需要提交时，仍按原子批次方式只触发一次部署。

## 6. 当前玩法实施路线

现在不按 Unity Runtime 阶段推进，而按玩法问题推进：

```text
阶段 A  人生经历阅读体验
连续年龄时间轴 / 单节点单故事 / memoryText

阶段 B  人物变化与连续性
Story Effect / LifeTag / Family / Occupation

阶段 C  世界反馈
桥梁、市场、天气、城市工程等 → 具体居民感受

阶段 D  有限并行生活线
允许轻量并行，重大故事互斥

阶段 E  内容规模验证
故事密度 / 重复率 / Coverage / 批量生产

阶段 F  玩家试玩迭代
根据实际体验调整 UI、文本密度和故事规则
```

## 7. main 更新规则

准备更新 `main` 前必须重新读取最新 `main` SHA。

禁止：

- 基于过期 main 创建 sibling commit 后强制覆盖；
- 同一逻辑功能按“一个文件一个 commit”推进 main；
- 为触发 Vercel 提交空 commit。

进入 `main` 的 commit 应代表一个完整、可验收的逻辑批次。

如果用户明确要求“现在提交一次以刷新线上版本”，可以在确认当前 main 未前进后，把必要的文档修正与已有代码状态放在 **一个** 新 commit 中提交；仍然只触发一次 Production Deployment。

---

## 8. 文档 / Schema / Code 同步规则

稳定玩法或内容字段发生变化时，应同步检查：

```text
玩法文档
+
Schema
+
Compiler / Validator
+
Web 消费代码
+
Visual Review
```

不能把旧设计继续写成当前事实。例如：

- 人生页已经取消年龄阶段分组，就不能再写“少年 / 青年 / 壮年分组 UI”；
- 人生故事已经使用 `memoryText`，就不能再写“历史页展开原始三阶段故事”；
- 本仓库已停止 Unity Runtime / Save 设计，就不能把它继续列为下一阶段工作。
