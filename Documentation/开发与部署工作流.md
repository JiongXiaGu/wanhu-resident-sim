# 开发与视觉审查工作流

正式回归使用 GitHub Actions：Build、Resident Content Review、Avatar Visual Review。不依赖 Vercel、Preview 或 Production。

## 两级 Review

只修改 Face / Hair / Outfit / Expression 的 SVG 画稿、配色、局部轮廓时，可先在确认的源码版本集中修改，直接调用真实 `renderAvatar()` / Pack SVG 生成诊断图板，实际检查相关 Frame、组合和 320 / 96 / 64 / 48px，再继续聚合修正，不要求每个中间状态等待 Actions。

源码静态头像图不是概念图，但没有运行完整 React 页面，不能据此声称工坊、居民界面、LocalStorage、导入或对象绑定通过。图板必须明确标为静态诊断。

正式批次按影响范围走对应链路：

```text
居民内容 tmp-* 开发
→ Build

居民内容 PR / main
→ Build + Resident Content Review

头像素材 / Catalog / Renderer
→ Build + Avatar Visual Review

跨域 UI / 基础设施
→ Build + Resident Content Review + Avatar Visual Review
```

候选必须下载对应同 SHA Artifact 并实际查看关键截图；必要时修正并重跑，再重读 main、非 force 推进已审查提交，最后对新 main 做同范围回归。

允许 Git Data API create_blob/create_tree/create_commit/update_ref。禁止一文件一提交、空提交刷检查、force 覆盖并行 main。合入前 main 已有新工作时先整合再审查。纯文档改动不需要为了制造绿色状态额外跑回归；代码、数据、测试或 Review 脚本改变则按范围回归。

## Build

`.github/workflows/validate.yml` 安装依赖、构建 Content、上传 generated Artifact 并做 Web TypeScript/Vite build。generated 不手改，内容契约变更需同步 Schema、Compiler 和消费者。不得借此扩张 Unity ECS/Blob/正式 Save 架构。

### Resident Content Lab 内容工作流

当前内容生产主链：

~~~text
Content / Avatar Authoring
→ Schema / Stable ID / Reference Validate
→ Content Compiler
→ Coverage / Lint
→ Web Preview
→ 人工审查
→ Compiled Content
→ Unity 消费
~~~

Web 不再承担正式居民模拟算法。

Action Presentation、LifeEvent、姓名、职业、LifeTag、Profile 和头像素材都是内容资产；Need、Schedule、Utility、Behaviour、目标搜索、预约、导航、经济、正式 RecentAction / LifeEvent Trigger 属于 Unity。

现有 ResidentGenerator、确定性 Action Trace 与 Tools/ResidentActionLife/record-policy.mjs 只作为稳定 Preview Fixture / 回归输入保留，不再作为功能演进主线。除修复预览与契约外，不新增游戏规则。

### Recent / LifeChapter 展示语义修正工作流

LifeEvent V3、Stage 移除、Snapshot V6 和统一“最近”已经完成。

当前先解决一个展示职责问题：

~~~text
当前
LifeEvent.text
→ 最近里显示标题 + 较长正文

目标
LifeEvent.recentText
→ 最近里只显示一句短记录

LifeEvent.memoryText
→ 只在人生经历 Story Chapter 展开
~~~

在该修正完成前暂停新的 LifeEvent 扩库。

#### Stage A · Contract / Data

只处理：

- LifeEvent Schema；
- 当前 26 条 LifeEvent；
- ContentContractCompiler / LifeEventCompiler；
- TS Domain；
- 必要 Coverage / Contract 断言。

目标：

~~~text
text
→ recentText
~~~

要求：

- recentText 一句话，通常约 12～36 个中文字符；
- recordToHistory = true 的事件继续保留 memoryText；
- 不新增 LifeEvent；
- 不保留 text fallback；
- 不改 Trigger / Utility / Behaviour。

Stage A 在 tmp-* 只跑 Build。

#### Stage B · Resident Panel / Review

只处理：

- “最近”从 LifeEvent title + 正文改成单句；
- RecentAction 与 RecentLifeEvent 使用相近的信息密度；
- Life History 继续只在 Story Chapter 展开 memoryText；
- 更新 capture-resident-review；
- 增加“最近不得显示长故事 / title + body”的断言。

Stage B 在 tmp-* 仍只跑 Build。

#### PR / main 边界

Stage A + B 完成后：

~~~text
Pull Request → main
→ Build
→ Resident Content Review
→ 下载同 SHA Artifact
→ 实际查看“此刻 / 最近 / 人生经历”
→ 重读 main
→ merge

merge → main
→ Build
→ Resident Content Review
→ 最终 Artifact 核对
~~~

Resident Content Review 不对每个 tmp-* push 自动执行，避免小改动反复安装字体、Playwright、启动浏览器与上传截图。

只有实际修改头像 / Portrait 跨域文件时才需要 Avatar Visual Review。

### 修正完成后的内容生产

内容生产分成两条独立路线，不再用一个中长度正文同时服务两个界面。

#### Recent 内容批次

主要补：

- Action Presentation；
- LifeEvent recentText。

特点：

- 高频；
- 一句话；
- 快速扫读；
- 优先反映居民最近做过什么。

如果内容本质上就是已有 Behaviour，优先补 Action Presentation，不重复建立 LifeEvent。

#### Life History 内容批次

主要补：

- Fact Chapter；
- recordable LifeEvent；
- memoryText；
- 结构事实 / LifeTag 驱动的弱关联人生故事。

特点：

- 低频；
- 稀疏；
- 多年后仍值得知道；
- Tag / 结构事实只决定候选资格；
- 故事真正发生后写入 LifeChapter；
- 打开人生页时不根据当前 Tag 重新计算过去。

建议 Life History 内容每批 4～8 条，避免一次写太多长故事；Recent 短句可以按 Coverage 采用 8～12 条小批。

### Review 分层目标

后续高频内容生产需要拆分审查职责：

~~~text
纯文档
→ 不需要视觉回归

居民内容 tmp 开发
→ Build

居民内容 PR / main
→ Build + Resident Content Review

头像素材 / Catalog / Renderer
→ Avatar Visual Review

跨域 UI / 基础设施
→ 两边按影响范围回归
~~~

Review 拆分已经完成：`.github/workflows/resident-content-review.yml` 负责居民内容，`.github/workflows/avatar-visual-review.yml` 负责头像；旧 `.github/workflows/visual-review.yml` 已移除。纯文档不在两套视觉 Review 的路径触发范围内。

代码、内容或 Review 变更继续使用 tmp-* 分支；generated 文件不手改。纯文档变更按本文件前述规则不需要为了制造绿色状态额外等待视觉回归。

居民行为语义仍遵守：

- 财富、职业、性格、年龄通常改变 Unity 中的成本、时间、机会或 Utility，不作为内容层的娱乐 / 社交 / 旅行硬白名单。
- 现实硬约束由 Unity 判断。
- RecentAction 的丰富度来自真实 Behaviour 种类；Action Presentation 通常只需要少量 Variant。
- Web 内容层不为了让界面“看起来丰富”而模拟不存在的行为。

## Review 职责

| 脚本 | 职责 |
| --- | --- |
| capture-resident-review | **Resident Content Review**：CurrentAction、“最近”单句密度、LifeChapter / memoryText、结构事实 / LifeTag 连续性与 Action Presentation 展示 |
| capture-portrait-review | 冻结正式 fallback 的六 Frame 与组合契约 |
| capture-avatar-review + audit-packs | Catalog 全组合、头型/头发/图层/兼容、对象保存和真实 UI |
| review-avatar-integration | 入口、延迟导入、应用后切对象与原子目标切换 |
| capture-avatar-art-polish | 全 Frame × Face × Expression 腮红及负对照 |
| capture-avatar-foundation | 六框架自由创作、独立保存、草稿切换、随机与历史筛选 |
| capture-avatar-age-wardrobe | 8B1 童老逐项 UI / 画稿和保留成年样板 |
| capture-avatar-adult-wardrobe | 8B2 明确历史 ID 的点选、衣领专项、旧新隔离对照 |
| capture-avatar-theme-assets | 8D1 明确新增清单、全库描述、检索、保存/JSON/绑定、旧稿不变 |
| capture-avatar-age-themes | 8D2 童老独立新增、metadata、四 Frame 点选/保存/JSON/绑定、132 份旧稿不变 |

原脚本的有效断言保留；新资产不能通过删除旧断言来过 CI。8B2 点选和旧新变化清单只覆盖其明确历史资源，8D1 新 ID 用增量脚本及通用全组合覆盖。组合数动态计算，不写死旧素材总数。

`export-age-baseline.mjs` 从完整 SHA 的 Git archive 临时导出头像源码，用 TypeScript 执行旧 Renderer，并在 finally 清理临时目录。旧画稿只进入 Artifact，不重新注册 Pack。8B1 对照基线为 `28ad42619edb7a6abb21ca7ef8d2dee30d2afda2`，8B2 为 `59028b3afd4b24c1cc57edbe68ce13b2bd5314f9`，8D1 冻结检查为 `7ba57695c392f14d598e818beadecff877dd52f9`。

8D1 要求旧基线 88 份固定渲染不变，新 32 ID/44 份适用画稿全部点选。100 个可选资产有中文描述/关键词，文本搜索匹配真实 Catalog。32 个新项还校验显式 theme / silhouette / 相似旧 ID / 差异 / 三尺寸识别信息，并与逐项文档同行核对。新 Hair 加弧线余量抽样，衣装检查作者层。几何签名仅排除完全相同路径的换色副本，不证明审美差异。

通用密度上限为每类 22，增量审查另保留童老 12 项边界；实际成年搜索/滚动界面必须人工查看。不得把上限当作无限扩量许可。

## Artifact 和实际看图

`content/source-commit.txt` 与 `content/source-and-contract.zip` 属于 Resident Content Review；`avatar/source-commit.txt` 与 `avatar/source-and-contract.zip` 属于 Avatar Visual Review。两套 Artifact 都必须能追溯精确 SHA。`avatar/` PNG 保留原尺寸，不参与根目录 legacy 预览压缩。

8D1 正式批次必须实际打开 `avatar/phase8d/` 四主题 `common/labor/merchant/traveler.png`、`phase8d-overview.png`、`faces-and-collars.png`、八张 `studio-<theme>-<frame>.png` 和 `bound-resident.png`。还须查看八张 studio-all 首尾截图，避免只审搜索后少数选项。native/ 保存全部 44 份新增适用画稿的三尺寸 PNG，共 132 张，逐图检查真实像素宽高。核对小尺寸和全部适用 Frame；继续查看原六框架保存/绑定与腮红、童老回归图。文字导出 `asset-descriptions.json` 只读，不手写回 Catalog。

必须区分静态 Renderer 诊断与完整浏览器真实 UI。不能把生成了截图写成看过，也不能以机器报告 PASS 替代人工查看。帽身被截断、领口悬空、肩线突折等可见问题需要继续修。

人工以桌面为主。移动端不再截图或列为必看项，390/320px 基础溢出 smoke 可保留。正式保存、导入、对象与居民逻辑测试不能用静态图替代。

## 交付

先写完成范围、main SHA、Build 与实际触发的 Review 真实结果、是否下载并查看同 SHA Artifact，以及实际 UI / 图板看了哪些。必要时贴少量关键截图，区分“已实现”“候选美术待验收”“未实施”。

用户当前自行从 GitHub 拉 main 进入网页测试，**不交付压缩包**。执行者内部仍下载并审查 Artifact，此要求不变。没有对应 run 就明确未验证，不用旧 run 冒充；8D2 已获授权；不提前开始 8C 或 Unity 迁移。

## 8D2 童老扩库的增量门禁

当前从 `70ca1ccd9cc5fa75491267ce29d20043df942994` 承接 8D2，儿童、老人各 6 Hair / 6 Outfit。独立年龄源文件不复用成年画稿。旧 8B1 回归用明确历史 ID 核对重画筛选，旧 8D1 回归只把其自己的新增清单当作增量；通用 Review 仍遍历实时 Catalog、描述与原有契约，不能删除旧断言。

新 step 先从同 SHA 临时导出 baseline，再运行 capture-avatar-age-themes。必须验证 132 份旧固定配方不变、32 次新 Frame / 资产点选、24 份完整 metadata 与文档行、144 次 Frame 适用性 / 确定性回退、192 次跨 Face 图层不变、1312 个头型边界抽样位置。童老原 12 项密度上限不提高，实际最大 10。四次 JSON 往返和四种真实居民绑定不改身份或日期，恢复仅删除当前覆盖。

avatar/phase8d2/ 有 11 张静态图板、28 张真实桌面图（八张筛选、十六张未筛选首尾、四张绑定）及 96 张 native/ 原尺寸输出。下载核 source-commit 后实际打开查看，尤其是头巾外包络、低髻与耳位、衣领连接及列表末项。source-and-contract.zip 自动包含新源文件和阶段文档。候选和 main 两轮流程不变，最终美术仍交用户验收。
