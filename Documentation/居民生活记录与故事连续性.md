# 居民生活记录与故事连续性

## 目标

居民界面不以“当前故事”为中心，也不维护人工拼接的“综合近况”。

玩家看到三个时间层次：

```text
这个人此刻在做什么
这个人最近发生了什么
这个人这一生经历过什么
```

故事是人生中的片段。多个不同时间发生的故事共同组成一个人的一生。

---

## 三层关系

```text
Resident
├─ CurrentAction
├─ RecentAction
├─ Current Story Thread
└─ Major Life History
```

职责：

- `RecentAction`：真实完成行为的精选近期记录；
- `Story Thread / LifeEvent`：当前正在进行的一件连续事情；
- `Major Life History / Life Chapter`：值得长期回看的过去。

不把所有内容永久塞进同一条日志。

---

## RecentAction 不属于人生历史

RecentAction 只记录真实发生过的行为，例如：

- 去井边挑了水回来；
- 把攒下来的衣物拿去洗了；
- 下工后沿河散步；
- 去朋友家做客；
- 去市上买了粮食；
- 去外地探亲或旅行。

它们应该短、有限、可淘汰，不进入人生经历。

RecentAction 不拥有 Behaviour Eligibility。能否执行挑水、旅行、串门等行为已经由 Schedule / Utility / Behaviour 决定；记录系统只接收成功完成事实。几十年前一次普通散步或买粮不应该占据人生时间轴。

## Story Thread

一个 Story Thread 是一件连续发生的事情，例如服役：

```text
名册上轮到我了
↓
每天都在官道上搬石填土
↓
终于回到家里
```

三个 Stage 在 **生活模式** 中仍然是一件事的三个时间节点。

当前阶段完整展示，旧阶段只用于轻量恢复上下文；三个 Stage 不计算成三段人生经历。

故事完成后：

```text
普通事件
→ 短暂留在最近发生
→ 淡出
→ 不进入人生经历

重要事件
→ 形成一个 Life Chapter
→ 人生时间轴增加一个节点
```

---

## Life Chapter

Life Chapter 是玩家回看一个人的一生时真正看到的单位。

例如：

```text
13岁 · 第一次独自替家里办事
18岁 · 开始做木工
23岁 · 成了家
27岁 · 轮到我去服役
31岁 · 家里添了孩子
```

### 事实章节

由居民状态变化直接产生：

- 开始某份营生；
- 成婚；
- 家里添孩子；
- 搬家；
- 职业改变。

它们只需要 `年龄 + 标题`，不为了文学感强行补故事。

### 故事章节

来自重要 LifeEvent / Story Thread，例如：

- 第一次独自完成正式工作；
- 服役；
- 第一次独自办事；
- 孩子入学；
- 晚年形成新的生活去处。

故事章节通过 `sourceEventId` 找回对应 LifeEvent Definition，并在人生页显示它的 `memoryText`。

`memoryText` 是一段完整的第一人称回忆，不再在人生页重放三个 Stage。

---

## Stage Text 与 Memory Text

### Stage Text

描述事情正在发生时的过程。

用于生活模式：

```text
现在发生什么
↓
几天后怎样
↓
事情最后如何结束
```

### Memory Text

描述事情结束后，这个人会怎样记得它。

用于人生经历：

```text
25岁 · 孩子到了该认字的年纪

我开始问附近哪家私塾合适……后来有一天回家路上，他忽然把一家铺子的招牌念了出来……
```

Memory Text 不显示：

```text
Stage 1 / Stage 2 / Stage 3
起初 / 后来 / 最后
来源标签
```

同一件事在生活页和人生页可以有不同文本组织方式，这是刻意设计，不是重复数据错误。

---

## 人生时间轴

人生页只有一条连续时间轴：

- 按年龄从小到大；
- 不使用“少年 / 青年 / 壮年”等 UI 分组；
- 一个节点只代表一件事；
- Fact Chapter 一行显示；
- Story Chapter 可展开一段 `memoryText`；
- 最后保留“如今”。

故事选择内部仍然可以按年龄阶段建立候选池，但内部筛选阶段不应泄漏为人生页分类。

---

## 人生故事密度

不是所有居民都应该有同样数量的重大故事。

居民之间允许：

- 有的人一生只有少量关键节点；
- 有的人青年时期经历多；
- 有的人中年才出现明显转折；
- 有的人大部分时间平淡，只留下几个真实事实。

不要为了让时间轴“看起来满”而强行给每个年龄阶段塞故事。

人生页的留白也是可信度的一部分。

---

## 故事之间的弱关联

大多数故事独立完成。

少量重要结果留下 `LifeTag / Story Anchor`：

```text
served_military
first_independent_task
child_started_school
newly_married
```

未来故事读取少量标签，而不是扫描完整历史文本。

例如：

```text
轮到我去服役
↓
lifetag.served-military
↓
多年后：旧同伍进城了
```

这种弱关联足以让玩家感觉“过去真的存在”，不需要完整社会图。

---

## Prototype Effect 与连续性

重要故事不仅可以留下文本，还可以在 Web Demo 中真正改变人物：

```text
成婚
↓
spouse / Household 变化
↓
人生经历出现“这门亲事定下来了”
↓
newly-married LifeTag
↓
解锁“两个人一起过日子以后”
```

Web Prototype 可以直接修改 Demo Snapshot 来验证玩法，但这种实现不代表未来 Unity 架构。

---

## 当前活动与故事分离

`CurrentAction` 是当前真实行为，不是历史摘要，也不由 UI 根据职业猜测。

例如：

```text
FetchWater   → 正在井边打水
VisitFriend  → 正在朋友家做客
TakeWalk     → 正沿河散步
Travel       → 正在前往外地
```

LifeEvent 可以影响 Schedule / Utility 或提出 Story Action Request，但 UI 不覆盖真实行为。故事结束后，CurrentAction 继续由实际 Behaviour 决定。

## 玩家界面原则

生活模式：

1. 居民身份；
2. 当前活动；
3. 正在经历 / 最近发生；
4. 少量 RecentAction；
5. 人生经历入口。

人生模式：

1. 只看过去；
2. 按年龄升序；
3. 不显示 RecentAction；
4. 不显示当前故事；
5. Story Chapter 展开 `memoryText`；
6. 不把三个 Stage 拆成三个人生节点。

---

## 连续性写作要求

即使人生页最后使用 `memoryText`，Stage 2 / Stage 3 仍应具备基本独立可读性，因为玩家可能隔几天才看到下一阶段。

后续 Stage 首句尽量保留至少一个记忆锚点：

- 人物身份；
- 上次出现的物件；
- 地点；
- 上一次关键行动。

`memoryText` 则应重新组织整件事，减少阶段文本之间的重复和复盘式措辞。

---

## 当前验收重点

继续试玩时主要观察：

- 人生节点数量是否自然；
- 从小到大阅读是否顺畅；
- 每个节点是否只讲一件事；
- 回忆是否像角色自己的话；
- 重要经历是否真的影响后续；
- 普通日常是否会自然淡出；
- 连续查看多个居民后是否明显重复。
