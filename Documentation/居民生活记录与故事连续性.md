# 居民生活记录与故事连续性

## 目标

居民界面不以“当前故事”为中心，而以“这个人最近过得怎么样”为中心。

故事是居民生活中的重要经历，不是挂在居民身上的任务卡。玩家点击居民时，应先感受到居民的身份、此刻活动与最近生活，再从生活记录中发现故事的延续。

## 核心数据关系

```text
Resident
├─ Identity
├─ CurrentState
├─ CurrentActivity
├─ RoutineSimulation
├─ StoryThreads
└─ LifeLog
```

`LifeLog` 是玩家界面的主要读取源。故事节点、普通日常、状态变化都进入同一条时间线。

## Story 与 LifeLog

一个三阶段故事仍保持固定事件树：

```text
Stage 1
  ↓
随机选择一个 Branch
  ↓
Stage 2
  ↓
Stage 3
```

但每个已发生节点都永久追加到居民 `LifeLog`，不能因为故事推进而覆盖上一个节点。

例如：

```text
Day 120  Story A / Stage 1
Day 127  Routine
Day 157  Story A / Stage 2
Day 164  Routine
Day 207  Story A / Stage 3
```

玩家在 Day 207 第一次查看居民，也应能看到 Stage 3 的正文，并能在同一面板中看到 Stage 2 / Stage 1 的前情。

## 玩家界面原则

玩家界面不显示：

- Story ID
- Branch ID
- Stage 编号
- D+ 时间表达
- 分支数量
- 三阶段进度点
- “这段经历还会继续”等剧本结构提示

这些信息只属于开发与审查界面。

玩家界面默认显示：

1. 居民身份
2. 当前活动
3. 最近生活记录
4. 最新的重要故事节点完整正文
5. 同一故事的旧节点折叠摘要
6. 普通生活的一行记录
7. 往事入口

## 最近生活记录

生活记录分为三类：

### Story

人工编写的重要生活事件节点。

最新 Story 节点完整展开；旧节点只显示标题与短摘要。

### Routine

背景模拟生成的普通生活记录，例如：

- 去早市买了些东西
- 下雨后提前收工
- 清点了一遍铺里的货
- 和邻居在巷口说了一会儿话

Routine 应短小，不承担复杂剧情，主要作用是让居民生活在正式故事之间保持连续。

### State

故事结果真正改变居民状态时记录，例如：

- 职业改变
- 家庭成员改变
- 居住关系改变
- 工作地点改变

State 变化必须同时更新居民当前数据，不能只留在故事文本里。

## 连续性写作要求

UI 会保留前情，但 Story Stage 2 / Stage 3 仍应具备基本的独立可读性。

后续节点首句应尽量包含至少一个“记忆锚点”：

- 人物身份
- 上次出现的物件
- 地点
- 上一次关键行动

例如：

不推荐：

> 几日后，他又来了。

推荐：

> 几日后，酒坊掌柜抱着那只小口试坛回来了。

这样即使玩家隔了一段现实时间重新查看，也能快速恢复上下文。

## UI 信息密度

真实验证以约 400px 宽的左下居民面板为基准。

最新故事节点：

- 标题尽量不超过 2 行
- 正文 2～4 行理想
- 5 行可接受
- 6 行开始警告
- 7 行以上优先考虑精简

旧故事节点只显示标题与一行摘要；普通 Routine 只显示一行。

最终应以实际渲染行数而不是单纯中文字数作为 UI 密度判断依据。

## 设计目标

玩家不应感觉：

> 我点了一个 NPC，看到了他携带的一篇故事。

目标体验是：

> 我点了一个居民，看看他最近过得怎么样；原来上次那件事后来又有了变化。
