# 网页居民模拟与数据组织

## 目标

Web 不是另起一套居民规则，而是用来验证未来 Unity 居民系统的表现与数据契约。

网页需要解决三件事：

1. 快速生成一批可重复的居民
2. 用真实游戏尺寸验证居民 UI 与 LifeLog
3. 让数据格式未来可以继续被 Unity 导出流程复用

网页层可以比 Unity Runtime 更方便调试，但不能反过来要求 Unity 使用低效的数据结构。

---

## 三层结构

整个仓库的数据建议分成三层：

```text
Content / Definitions
        ↓
Generator / Compiler
        ↓
Generated Snapshot
        ↓
Web UI
        ↓
未来 Unity Export
```

### 1. Content / Definitions

人长期维护的源数据。

包括：

- 姓名词库
- 职业定义
- Routine 模板
- 居民生成规则
- Story Markdown

这些文件追求可读、可审查、可版本管理。

### 2. Generated Snapshot

由工具自动生成的验证数据。

Web 不需要每次运行都自己理解全部源文件规则，而是读取标准化快照。

### 3. Web UI

Web 只负责：

- 展示居民
- 推进时间
- 调用模拟器
- 查看 LifeLog
- 检查 UI 密度
- 暴露开发信息

## 源数据设计

### Names

姓名允许重复，因此数据非常简单。

```json
{
  "schema": "wanhu.names.v1",
  "surnames": ["沈", "吴", "陈", "周", "赵"],
  "maleGivenNames": ["安", "砚", "桥", "榆"],
  "femaleGivenNames": ["荷", "贞", "岚", "宁"]
}
```

V1 不做全城唯一性检测。

生成结果只要求同一个 `ResidentSeed` 每次得到同一个姓名。

### Occupations

职业定义保持稳定 ID，显示名称可以修改。

```json
{
  "schema": "wanhu.occupations.v1",
  "items": [
    {
      "id": "occupation.cloth-worker",
      "name": "布庄伙计",
      "workplaceType": "shop.cloth",
      "minLifeStage": "young-adult"
    },
    {
      "id": "occupation.potter",
      "name": "陶工",
      "workplaceType": "workshop.kiln",
      "minLifeStage": "young-adult"
    }
  ]
}
```

源定义只描述职业本身，不把具体某个居民写进职业文件。

### Routine Templates

Routine 是短小、低成本的生活表现。

```json
{
  "schema": "wanhu.routines.v1",
  "items": [
    {
      "id": "routine.potter.check-kiln",
      "occupation": "occupation.potter",
      "text": "天没亮就去看了一遍窑火",
      "weight": 1
    }
  ]
}
```

后续可扩展简单条件：

```json
{
  "weather": ["rain"],
  "season": ["summer"]
}
```

条件仍只读取居民自己和 GlobalSnapshot。

### Resident Generation Rules

不要把概率散落在 Web 组件里。

```json
{
  "schema": "wanhu.resident-generation.v1",
  "daysPerYear": 360,
  "lifeStages": [
    { "id": "teen", "minAge": 13, "maxAge": 17 },
    { "id": "young-adult", "minAge": 18, "maxAge": 29 },
    { "id": "adult", "minAge": 30, "maxAge": 44 },
    { "id": "middle-age", "minAge": 45, "maxAge": 59 },
    { "id": "elder", "minAge": 60, "maxAge": 120 }
  ],
  "recentLifeLogCapacity": 12
}
```

以后 Unity 可以使用同样的稳定定义，再编译成更适合 Runtime 的 Blob / 数值结构。

## Web 生成快照

网页不直接把源定义当居民实例。

推荐生成：

```text
Web/public/generated/resident-snapshot.json
```

示例：

```json
{
  "schema": "wanhu.resident-snapshot.v1",
  "citySeed": 102938,
  "currentDay": 12480,
  "residents": [
    {
      "id": 1001,
      "seed": 88421,
      "displayName": "沈荷",
      "birthDay": 240,
      "gender": "female",
      "portraitSeed": 55219,

      "occupationId": "occupation.cloth-worker",
      "workplaceId": 301,
      "employmentStartDay": 11200,

      "householdId": 81,
      "fatherId": 0,
      "motherId": 0,
      "spouseId": 1002,
      "childCount": 2,

      "nextUpdateDay": 12483,
      "stateBits": 0,
      "activeStoryId": null,

      "recentLifeLog": [],
      "majorLifeHistory": []
    }
  ],
  "households": [
    {
      "id": 81,
      "homeId": 920,
      "memberIds": [1001, 1002, 1003, 1004]
    }
  ]
}
```

这里有意把 `households` 独立出来。

居民高频状态不需要包含可变长度的家庭成员数组；只有 UI 或低频家庭系统需要时才查询 Household。

## Web Snapshot 与 Unity Runtime 不必一模一样

这是重要边界。

Web Snapshot 可以为了调试方便包含：

- displayName
- memberIds
- 完整 LifeLog
- 原始字符串 ID

Unity Runtime 最终可以编译成：

```text
StableHash / ushort / enum / bitmask / BlobAsset / DynamicBuffer
```

例如 Web：

```text
"occupation.cloth-worker"
```

Unity Runtime 可以变成：

```text
OccupationId = 17
```

只要两边来自同一套定义和稳定 ID 即可。

## Web 中的居民生成

第一阶段建议不要一上来生成几千居民。

默认生成：

```text
CitySeed + 50 Residents
```

这样方便快速人工检查。

生成流程：

```text
CitySeed
  ↓
ResidentId
  ↓
Hash(CitySeed, ResidentId)
  ↓
ResidentSeed
  ↓
姓名 / BirthDay / PortraitSeed / 职业 / 家庭背景
```

同样的 CitySeed 应得到同样的一批居民，方便截图对比和 Bug 复现。

DEV 面板可以提供：

- 重新生成 CitySeed
- 输入固定 Seed
- 上一个/下一个居民
- 推进 +1 / +10 / +100 天
- 强制执行一次 Life Update
- 强制触发 Story
- 查看原始居民数据

## 网页玩家视图

玩家态继续使用当前验证过的左下约 400px 面板。

### Header

只显示最重要身份：

```text
头像  沈荷
      34岁 · 布庄伙计
      河东坊 · 已婚 · 两个孩子
```

### 当前状态

```text
此刻
正在铺里清点今日新到的布
```

这句话优先在点击时推导，不要求后台持续模拟逐小时 Activity。

### 最近生活

```text
最近

今日
掌柜让我第一次独自决定这一批布怎么进。
[完整正文]

3日前
回家时给孩子带了一包糖。

7日前
下雨，铺子比往常早关门。

18日前 · 前情
丈夫离家近三年，一直没有消息。
```

规则：

- 最新重要 Story 节点完整显示
- 同一 Story 的旧节点显示短摘要
- Routine 一行显示
- State Change 作为“生活变化”显示
- 不显示 Branch / Stage / D+ 等开发结构

### 往事

底部只保留入口：

```text
往事 14 >
```

展开后才读取更多历史记录。

## 推荐 Web 代码边界

不要继续把生成、模拟、UI 全写在 `App.tsx`。

建议逐步拆为：

```text
Web/src/
├─ domain/
│  ├─ resident.ts
│  ├─ household.ts
│  ├─ occupation.ts
│  └─ life-log.ts
│
├─ data/
│  └─ generated-data.ts
│
├─ simulation/
│  ├─ resident-generator.ts
│  ├─ resident-life-update.ts
│  ├─ current-activity.ts
│  └─ story-selector.ts
│
├─ resident/
│  ├─ ResidentPanel.tsx
│  ├─ ResidentHeader.tsx
│  ├─ ResidentLifeFeed.tsx
│  └─ ResidentHistory.tsx
│
├─ review/
│  ├─ DevPanel.tsx
│  └─ StoryReviewView.tsx
│
└─ App.tsx
```

其中 `simulation/` 尽量写成纯函数，输入数据，输出结果，不依赖 React。

这样以后这些规则更容易迁移为 Unity 实现或作为算法参考。

## 未来扩展顺序

建议按以下顺序增长，而不是一次做完整社会模拟：

### V1

- 姓名
- BirthDay / 年龄
- 职业
- 工作地点
- 家庭/家谱引用
- 稀疏 Life Update
- Routine
- LifeLog
- Story

### V1.1

- 职业变化
- 出生 / 结婚 / 死亡结构命令
- Household 展示
- MajorLifeHistory

### V1.2

- 区域状态影响
- 天气 / 季节影响 Routine
- 更完整的 Story Effect

除非游戏体验验证明确需要，否则不增加全城关系传播与复杂 Needs。
