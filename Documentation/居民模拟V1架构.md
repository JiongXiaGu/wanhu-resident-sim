# 居民模拟 V1 架构

## 目标

《万户天工》的居民系统不追求完整社会仿真，而追求一种更适合大型城市模拟游戏的结果：

> 每个居民拥有一条自洽、低成本、可回看的个人生命轨迹。

玩家点击居民时，应能自然理解：这个人是谁、今年多大、靠什么生活、和谁组成家庭、现在在做什么、正在经历什么，以及过去哪些经历留下了痕迹。

系统必须优先保证数千居民的并行更新能力，因此不建立高频社会关系网，不进行居民之间的状态传播。

本文件描述的是 **正式 Runtime 的架构方向**。当前 Web Demo 用于验证玩法和内容，不要求与 Unity ECS 使用相同物理数据结构。

---

## 1. Prototype 与 Runtime 边界

### Web Demo

Web 可以为了快速验证保留：

- JSON
- 字符串 ID
- `displayName`
- `portraitSeed`
- `currentAction`
- `recentActions`
- 固定 CitySeed Snapshot
- DEV 面板与快速推进

这些都是原型工具。

### 正式 Unity Runtime

正式游戏目标：

- Authoring Data 在构建前编译。
- Definition 进入只读 `ResidentContentBlob`。
- Resident Entity 只保存必要状态。
- Runtime 不解析 Markdown / JSON。
- 存档不复制故事正文、职业名称、姓名字符串或头像图片。

详细内容管线见：

```text
Documentation/居民内容生产与运行时数据管线V1.md
```

## 2. 核心原则

### 2.1 居民独立并行

常规居民更新只允许读取：

- 自己的居民状态
- 全局只读世界快照
- 编译后的少量只读 Definition

常规模拟不遍历其他居民，不沿家庭、朋友、同事关系传播状态。

```text
GlobalSnapshot
      │
      ├──────────────┬──────────────┐
      ↓              ↓              ↓
 Resident A      Resident B      Resident C
      ↓              ↓              ↓
 只改自己状态      只改自己状态      只改自己状态
```

### 2.2 允许关系引用，不允许关系网络计算

居民可以保存父母、配偶、Household 等引用，因为这些数据对家谱、UI、故事条件和低频结构变化有价值。

但引用本身不意味着运行时传播。

### 2.3 高频模拟与低频结构变化分离

结婚、出生、死亡、搬家等会修改多个对象，但它们是低频结构事件。

Resident 并行 Job 只输出命令：

```text
MarriageCommand
BirthCommand
DeathCommand
MoveHouseholdCommand
ChangeOccupationCommand
```

随后由集中结构系统统一处理结构变化。

### 2.4 稀疏调度

每个居民保存：

```text
NextUpdateDay
```

只有达到更新时间的居民才进入 Life Update。

### 2.5 年龄由 BirthDay 推导

长期保存 `BirthDay`，不保存需要每天更新的 `Age`。

```text
Age = (CurrentDay - BirthDay) / DaysPerYear
```

### 2.6 当前活动优先推导

当前活动不再由 UI 根据职业、时间、天气或故事文本推导。

正式语义：

```text
CurrentAction
├─ ActionType
├─ TargetResidentId? / TargetEntityId?
├─ PlaceId?
└─ Phase
```

Schedule / Utility / Behaviour 决定当前正在做什么，UI 只读真实 CurrentAction。例如 FetchWater → “正在井边打水”，VisitFriend → “正在朋友家做客”，Travel → “正在前往外地”。

LifeEvent 可以影响 Schedule / Utility 或请求 Story-specific Action；UI 不覆盖实际行为。Web Demo 使用确定性的测试 CurrentAction / Action Trace，但不得根据职业在 UI 层猜测行为。

### 2.7 Definition 与实例状态分离

故事正文、姓名文本、职业名称、Action Presentation、头像资源定义都属于 Definition。

Resident 实例只保存：

- Stable ID / RuntimeIndex
- 当前状态
- 少量 Story Thread
- 少量 Life Chapter
- 外观最终选择结果

## 3. Runtime 数据分块

### 3.1 ResidentIdentity

创建后基本稳定：

```text
ResidentIdentity
├─ ResidentId
├─ Seed
├─ BirthDay
├─ SurnameId
├─ GivenNameId
└─ Gender
```

姓名允许重复，不进行全城查重。

正式 Runtime 不需要为每个 Entity 永久保存完整 `displayName` 字符串；UI 显示时从 Name Definition 组合。

### 3.2 ResidentSimulationState

高频 / 稀疏更新的核心状态：

```text
ResidentSimulationState
├─ OccupationIndex
├─ WorkplaceId
├─ HouseholdId
├─ NextUpdateDay
├─ StateBits
└─ LifeTagBits
```

LifeTag 用于压缩过去的重要经历，例如“曾服役”“学过木工”“曾负债”。

### 3.3 ResidentFamily / Household

家庭引用属于冷数据：

```text
ResidentFamily
├─ HouseholdId
├─ FatherId
├─ MotherId
├─ SpouseId
└─ ChildCount
```

完整 Household 成员列表应由 HouseholdStore / Buffer 持有，不塞入高频主状态。

### 3.4 ResidentAppearance

正式版不只保存 `PortraitSeed`。

Seed 只负责第一次生成；最终保存稳定的 Appearance DNA：

```text
ResidentAppearance
├─ FaceId
├─ HairId
├─ BrowId
├─ BeardId
├─ HeadwearId
├─ OutfitId
├─ SkinPalette
├─ HairPalette
├─ ClothingPalette
└─ FeatureFlags
```

这样以后扩充资源池也不会让老居民改变长相。

UI Portrait 和世界 3D Character 应共享关键识别特征，但可以使用不同渲染实现。

### 3.5 Story Thread

当前正在运行的少量故事放在 Buffer / 冷数据中：

```text
ResidentStoryThread
├─ EventId / RuntimeIndex
├─ StartDay
├─ Stage
├─ NextStageDay
└─ Small Payload
```

不把完整故事正文复制进居民。

### 3.6 Life Chapter

长期保存的重要人生章节：

```text
ResidentLifeChapter
├─ Day
├─ Type
├─ EventId / StableId
├─ Variant / Outcome
└─ Optional Payload
```

UI 展开故事时通过 Event ID 查询 `ResidentContentBlob` 的文本。

---

## 4. Hot / Cold 数据分离

### Hot

普通 Life Update 高频读取：

- NextUpdateDay
- StateBits
- LifeTagBits
- Occupation / Household / Workplace 紧凑索引

### Cold

低频访问：

- Identity 文本引用
- 家庭详细引用
- Appearance DNA
- StoryThread Buffer
- LifeChapter Buffer

运行时避免为了一个普通 Life Update 把完整居民资料全部拉入缓存。

---

## 5. ResidentContentBlob

正式 Unity 只读内容目标：

```text
ResidentContentBlob
├─ Names
├─ Occupations
├─ ActionPresentations
├─ LifeEvents
├─ LifeTags
├─ LifeStages
├─ StoryBuckets
├─ TextTable
└─ Portrait Rules / Asset References
```

Authoring JSON / Markdown 在构建前经过 Compiler；Runtime 不直接解析源文件。

Web Demo 可以从同一个 Authoring Source 导出自己的 JSON Bundle。

---

## 6. 全局只读世界快照

居民通过统一 World Snapshot 感知城市，而不是互相查询。

可逐步包含：

```text
CurrentDay
Season
WeatherBand
FoodPriceBand
EmploymentBand
CityProsperityBand
DisasterFlags
DistrictState
WorldTags
```

例如：

```text
连续降雨 / 道路拥堵 / 设施关闭
→ Utility / Behaviour 成本和机会发生变化
```

或者：

```text
北河新桥建成
→ WorldTag: bridge.opened.north_river
→ 附近居民在低频更新时可能抽到相关 LifeEvent
```

世界系统不需要主动遍历所有居民去“发故事”。

---

## 7. RecentAction 的运行时策略

近期生活只记录真实 Behaviour 完成事实。

```text
Behaviour Complete
→ ResidentActionCompletedEvent
→ RecordPolicy
→ RecentAction 小环
```

Action Completed Event 至少包含 ResidentId、ActionType、Day/Tick，并可直接携带 Behaviour 已经确定的 TargetResidentId / TargetEntityId / PlaceId。RecentActionRecordSystem 不做职业、年龄、财富、家庭、天气 Eligibility，也不重新寻找目标。

只有存在 Presentation 且通过轻量记录策略的 Action 才进入“最近”。普通吃饭、每一段走路等高频行为可以不展示；看病、串门、散步、旅行、挑水、洗衣、购物等按真实玩法需要记录。

财富、职业、年龄、性格主要影响 Behaviour 的 Utility、成本、时间预算和机会，不硬编码“穷人不能旅行”“老人不能娱乐”等内容白名单。真实生活是否单调应由城市条件和居民状态自然产生。

## 8. StorySelector

StorySelector 只读取：

```text
AgeStage
Occupation / OccupationGroup
LifeTagBits
StateBits
FamilyState
WorldSnapshot
```

Compiler 预先建立 `StoryBucket`，Runtime 不扫描全内容库。

```text
AgeStage + OccupationGroup
↓
候选 Bucket
↓
Tag / Family / World 条件过滤
↓
加权抽取
```

Story 结果可以：

- 修改当前居民状态
- 增删 LifeTag
- 记录 Life Chapter
- 请求换工作 / 搬家 / 结婚 / 生子等结构变化

涉及多 Entity 的修改必须输出集中结构命令。

## 9. 生命周期更新流程

```text
1. Scheduler
   NextUpdateDay <= CurrentDay

2. ResidentLife Job
   - 读取 Resident Hot State
   - 读取 ResidentContentBlob
   - 读取 WorldSnapshot
   - 推进现有 StoryThread
   - 判断是否需要抽取新 Story
   - 更新自己的状态与 NextUpdateDay
   - 输出 Structural Request

3. Structural Systems
   - 结婚 / 出生 / 死亡 / 搬家 / 换工
   - 集中 ECB 结构修改

4. History / Tags
   - 重要结果写 LifeChapter
   - 重要经历留下 LifeTag
```

常规流程中不存在“居民 A 查询 B，再影响 C”的链式社会传播。

---

## 10. Save 原则

正式存档保存居民真实状态，不保存内容副本。

建议长期保存：

```text
ResidentId
Seed
BirthDay
Gender
SurnameId
GivenNameId
AppearanceDNA
Occupation StableId / Mapping
WorkplaceId
HouseholdId
StateBits
LifeTagBits
NextUpdateDay
StoryThread[]
LifeChapter[]
```

不保存：

```text
完整姓名字符串
职业显示名
故事标题 / 正文
Action Presentation 文本
头像图片
```

Definition 通过 StableId / StableIdHash 在当前版本的 Content Database 中解析。

## 11. “像活人”的最低成本来源

V1 不依赖复杂社会模拟，而依赖：

1. 姓名与家庭来源稳定
2. Appearance DNA 稳定
3. 年龄随时间真实增长
4. 职业、住处、家庭会真实变化
5. 少量 Story Thread 提供当前生活
6. LifeTag 让过去偶尔影响未来
7. Life Chapter 让玩家能回看一生
8. RecentAction 让玩家直接看到真实行为留下的生活轨迹

重点是让玩家相信居民“有过去、有现在、会变化”，而不是精确模拟每分钟的社会行为。

---

## 12. V1 明确不做

当前阶段不加入：

- 全城社交关系网
- 情绪传播
- 朋友影响朋友
- 同事网络模拟
- 高频家庭成员互相查询
- 为展示文本另建一套与真实 Behaviour 平行的 Needs / 决策规则链
- 每个居民逐小时完整日程
- 全城姓名唯一检查
- 无限增长 LifeLog
- Resident Entity 内复制故事正文
- Runtime 解析 Authoring JSON / Markdown

这些只有在明确证明能提高游戏体验且成本可控后才扩展。
