# 居民行为与最近生活记录

## 目标

《万户天工》的居民生活不由一套独立“日常内容生成器”分配，而由真实 AI 行为自然产生。

玩家看到的：

```text
此刻
最近
人生经历
```

分别对应：

```text
CurrentAction
RecentAction
LifeEvent / LifeChapter
```

这三层必须保持数据来源清晰。

## 核心链路

```text
Need / Household Need / Schedule / Opportunity
                ↓
             Utility
                ↓
            Behaviour
                ↓
找人 / 找地点 / 预定 / 移动 / 执行
                ↓
             Complete
                ↓
     ResidentActionCompletedEvent
                ↓
       RecentActionRecordSystem
                ↓
           RecentAction
```

例如缺水：

```text
Household.Water 低
→ FetchWater Utility 上升
→ 找最近可用水井
→ 预定取水点
→ 去取水
→ 挑回家
→ Household.Water 增加
→ 产生 FetchWater Completed
→ 最近显示“家里的水不多了，去井边挑了水回来。”
```

洗衣、买粮、串门、散步、看戏、旅行都遵守同一逻辑。

## 数据所有权

Behaviour 拥有：

- ActionType；
- 为什么执行；
- TargetResident / TargetEntity；
- Place；
- 预定与寻路结果；
- 成功 / 失败；
- 实际资源变化。

RecentActionRecordSystem 不拥有这些规则，只读取成功完成事件。

因此禁止：

```text
Recent 系统发现“需要 child Context”
→ 扫描所有居民
→ 找一个孩子
```

正确方式：

```text
CareChild Behaviour 已经有 TargetResident
→ Complete Event 直接携带 TargetResidentId
```

## Action Presentation

Presentation 只负责“怎样把一个已经发生的行为说给玩家看”。

推荐源：

```text
Content/ResidentActions/resident-action-presentations.json
```

建议结构：

```json
{
  "id": "resident-action.fetch-water",
  "cooldownDays": 3,
  "variants": [
    "家里的水不多了，去井边挑了水回来。",
    "去附近水井打了水，挑回家里备用。"
  ]
}
```

第一版不加入 Occupation、LifeStage、Wealth、Family、Weather Eligibility。

一个 Action 通常 2～4 条 Variant 即可。重复感优先通过居民真实行为种类解决，而不是为同一行为写几十条同义句。

## RecentAction RecordPolicy

不是每个 Behaviour Complete 都必须显示。

例如：

```text
普通走路
每顿吃饭
每次睡觉
```

可以不进入最近记录。

而：

```text
挑水
洗衣
买粮
看病
串门
散步
看戏
喝茶
探亲
旅行
```

通常具有更高观察价值。

轻量策略只需要：

```text
是否存在 Presentation
同 Action cooldown
避免相邻重复
固定容量 8～12
```

不再做复杂候选池与 Eligibility。

## CurrentAction

“此刻”来自真实 CurrentAction，不由 UI 推导。

```text
FetchWater   → 正在井边打水
WashClothes  → 正在洗衣
VisitFriend  → 正在朋友家做客
TakeWalk     → 正沿河散步
Travel       → 正在前往外地
```

LifeEvent 需要影响当前行为时，应作用于 Schedule / Utility / Story Action Request；UI 不拥有覆盖真实行为的字段。

## 居民自由与阶层差异

职业、财富、年龄、性格原则上不是娱乐 / 社交 / 旅行白名单。

它们应该影响：

```text
时间预算
金钱成本
可达性
需求速度
行为收益
Utility 权重
目标偏好
```

例如贫困居民不是“禁止旅行”，而是远途成本更高；附近探亲、短途郊游、免费庙会仍可能发生。富裕居民通常有更多时间和可支配收入，因此远途娱乐更容易，但不是专属权限。

只有现实硬约束才阻止行为：钱不够、设施关闭、目标不存在、不可达、容量满、身体状态不允许、任务互斥等。

居民生活允许不平均。一个居民长期工作、挑水、买粮、照顾家庭而几乎没有娱乐，本身就是有价值的生活状态；玩家可以由此产生同情并发现城市问题。改善道路、公共设施、收入、休息时间后，生活轨迹自然改变。

## 与 LifeEvent / 人生经历的边界

```text
CurrentAction  现在真的在做什么
RecentAction   最近真的完成过什么
LifeEvent      正在经历的一件连续叙事
LifeChapter    一生值得长期记住什么
```

普通 RecentAction 不进入人生经历。

重大结构事实和重要 LifeEvent 才形成 LifeChapter。

## Web Demo 边界

Web 不复制完整 Unity AI。

第一轮只使用少量确定性 Action Trace 验证：

- CurrentAction 能驱动“此刻”；
- Completed Action 能驱动“最近”；
- Target / Place 从 Action 传入；
- RecordPolicy 能控制密度；
- RecentAction 不进入人生历史；
- LifeEvent / LifeChapter 不受破坏。

真实 Utility、设施查询、预定、寻路和 Job 化 Behaviour 在 Unity 主工程实现。

## 当前实现状态

当前 Web / 内容管线已经建立：

1. Action Presentation Contract；
2. CurrentAction / ResidentActionCompletedEvent / RecentActionRecord；
3. 确定性 Action Trace 作为 Web 测试数据源；
4. Action Presentation Stable ID Registry；
5. RecentAction RecordPolicy、cooldown、容量与相邻去重；
6. Review 对 CurrentAction、RecentAction、targetResidentId、LifeEvent / LifeChapter 分层做回归；
7. Build Artifact 输出编译后的 Action Presentation 与 Resident Snapshot。

正式 Unity 行为系统接入时，只需把测试 Trace 替换成真实 Behaviour Complete 事件；当前树不维护已移除格式的兼容读取。

## 第一批代表行为

第一批只需要足以验证结构的行为：

```text
fetch-water
wash-clothes
go-to-work
buy-food
take-walk
visit-friend
visit-family
watch-performance
go-to-teahouse
travel
rest-at-home
```

后续每实现一个真实 Behaviour，再决定是否增加对应 Presentation。最近生活内容库应跟随真实 AI 能力增长，而不是先写出大量居民实际上不会执行的文案。
