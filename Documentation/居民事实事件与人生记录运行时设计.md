# 居民事实事件、最近行为与人生记录语义设计

## 目标

本文件只记录 Unity 主工程未来需要保持的语义边界，不规定具体 ECS、事件容器、调度算法或 Save 物理布局，也不是 Web Content Lab 的实施任务。

居民 UI 的“此刻”和“最近”必须来自真实模拟：CurrentAction 表示当前行为，RecentAction 表示已完成且值得展示的行为。

```text
Schedule / Utility / Behaviour
→ CurrentAction
→ Behaviour Complete
→ ResidentActionCompletedEvent
→ RecentActionRecordSystem
→ 最近的事情

LifeEvent
→ Story Thread
→ 重要结果
→ LifeChapter / LifeTag
```

Resident Content Lab 只用固定 Fixture 预览这条语义链；正式算法与数据结构由 Unity 主工程决定。

## Behaviour 是生活权威

行为树、Schedule、Utility 负责：

- 为什么做这件事；
- 什么时候做；
- 去哪里；
- 找谁；
- 目标是否可达；
- 是否需要预定；
- 行为是否真正完成。

例如：

```text
Household 缺水
→ Utility 选择 FetchWater
→ 找最近可用水井
→ 预定
→ 移动
→ 取水
→ 回家
→ Household 水增加
→ FetchWater Complete
```

“最近的事情”不能再反向推导这些条件。

## ResidentActionCompletedEvent

只在有意义的行为成功完成点写紧凑事件，不在行为树每个节点写日志。

建议语义字段：

```text
ResidentId
ActionType
Day / Tick
TargetResidentId? / TargetEntityId?
PlaceId?
Flags? / SmallPayload?
```

第一阶段不要为了理论完整性加入大量字段。Target / Place 必须由 Behaviour 自己提供；Recent 系统不得扫描家庭、朋友、地点或设施来补 Context。

具体事件容器、并发写入方式、容量策略与是否使用 NativeStream / NativeList / NativeQueue，由 Unity 主工程基于真实 Job 图、数据量与性能测试决定。本仓库只要求“行为完成后能提供紧凑事实”这一语义。

## RecentActionRecordSystem

记录系统只做：

```text
Action Completed
→ 是否存在 Presentation
→ 是否值得展示
→ 同 Action 轻量 cooldown / 相邻去重
→ 确定 VariantIndex
→ 写固定容量 RecentAction Buffer
```

不做：

```text
Occupation Eligibility
LifeStage Eligibility
Wealth Eligibility
Family Eligibility
Weather Eligibility
Context Resident Search
全 Action 库加权抽取
```

建议近期记录固定 8～12 条，小环自然淘汰。普通 RecentAction 不进入永久人生历史。

## Action Presentation

Action Presentation 是薄展示层，不是行为规则。

建议 Authoring：

```text
resident-action.fetch-water
resident-action.wash-clothes
resident-action.visit-friend
resident-action.travel
```

每个定义只需要少量展示信息，例如：

```text
Stable ID
recordPolicy / cooldownDays
variants[2..4]
```

文本不能决定居民是否有资格执行行为。行为丰富度主要来自真实 Behaviour 种类，而不是为同一行为写大量近义句。

## CurrentAction

玩家面板“此刻”读取真实 CurrentAction：

```text
FetchWater    → 正在井边打水
WashClothes   → 正在洗衣
VisitFriend   → 正在朋友家做客
TakeWalk      → 正沿河散步
Work          → 正在工作地点做工
Travel        → 正在前往外地
```

不要根据职业、休息日或 LifeEvent 文本在 UI 层猜当前活动。

LifeEvent 若需要改变当下行为，应影响 Schedule / Utility 或提出 Story Action Request，不能在 UI 层伪造当前行为。

## Utility 与生活差异

所有居民原则上都可以拥有工作、家庭、社交、娱乐、旅行等行为机会。财富、职业、年龄、性格通常影响：

- 时间预算；
- 金钱成本；
- 可达性；
- 行为收益；
- 需求产生速度；
- Utility 权重；
- 目标选择。

它们不应成为“能不能娱乐 / 社交 / 旅行”的硬白名单。

只有真实硬约束才阻止行为，例如钱不够、目标不存在、不可达、设施关闭、容量满、身体状态不允许或正在执行互斥任务。

因此一个居民长期只有工作、挑水、买粮、睡觉，也可以是可信模拟结果；玩家由此感受到生活压力。另一个居民经常散步、串门、看戏、旅行，则反映其时间、收入、设施和关系条件。不要为了 UI 好看强行平均分配娱乐。

## LifeEvent 与人生记录

LifeEvent 继续承担低频叙事，不和 RecentAction 合并。

长期历史仍只在两类时刻写入：

1. 结构事实真正成功：开始 / 换工作、成婚、添孩子、搬家等，写 Fact Chapter。
2. LifeEvent 完成且 `recordToHistory = true` 或带长期结构结果，写 Story Chapter。

LifeTag 负责“过去影响未来”，不扫描历史正文。

```text
RecentAction  → 近期真实行为，会淘汰
LifeEvent     → 当前连续叙事
LifeChapter   → 长期人生节点
LifeTag       → 紧凑连续性事实
```

## 保存边界

正式游戏可以保存必要的 RecentAction 小环，便于加载后保持近期生活连续性，但只保存紧凑事实：

```text
Day
ActionType / StableId Mapping
VariantIndex
TargetResidentId?
PlaceId?
```

不保存展示文本，不保存完整行为轨迹，不保存行为树临时节点。

CurrentAction / RecentAction 使用当前稳定契约；当前树不维护已移除近期生活格式的双轨兼容结构。

## Resident Content Lab 边界

本仓库只需要用固定 Fixture 证明以下内容可以被正确展示：

~~~text
CurrentAction
RecentAction
LifeEvent
LifeChapter
~~~

已有 Action Trace / RecordPolicy 可以继续为预览服务，但不再扩展为正式 Runtime，也不作为 Unity 的实现标准。

Action Presentation、LifeEvent 文本和 Stable ID 属于这里；Behaviour、Utility、设施预定、寻路、记录算法和运行时存储属于 Unity。
